# Linux bundle

## Goal

`make bundle` on Linux builds `bin/Hypercube/`, one directory for the host
architecture with the Electron client, `hypercube`, the four harness plugins,
the UI pages, a PNG icon, and a `.desktop` file. `make build` links
`bin/hypercube` and the plugins into it, and `make release` packs it as one
`tar.gz` with `SHA256SUMS`. macOS packaging keeps its current output.

A new Linux test, run in the Linux test container, builds the bundle and
checks its layout, runs `hypercube version` and the plugins from it, and
starts the backend from it. A CI job runs that test on `ubuntu-24.04`.

This task does not launch the desktop app (`desktop/dock.js` needs `app.dock`,
which Linux lacks; the desktop app task fixes that) and does not add the
service installer (the install and service task adds it to `resources/`).

## Related code

- `Makefile` — `bundle`, `build`, `release`, `install`, `place`,
  `quit-desktop`, and `install-service` build and install the macOS `.app`
  with `sips`, `iconutil`, `plutil`, `codesign`, `lsappinfo`, `osascript`, and
  `lsregister`. `binaries OUT=dir` builds `hypercube` and the plugins side by
  side. `make` with no target runs `bundle`, the first rule.
- `scripts/release` — checks the beta tag, HEAD, and a clean checkout,
  requires darwin/arm64, builds the bundle in `bin/release/`, checks
  `hypercube version`, verifies the signature, zips the app, and writes
  `SHA256SUMS`.
- `desktop/package.json` — the desktop app's package; Electron reads
  `productName` and `desktopName` from it.
- `desktop/main.js` — loads the pages from `process.resourcesPath/ui`.
- `internal/harness/discovery.go` — finds `hypercube-harness-*` executables
  beside the running `hypercube`.
- `plugins/internal/plugin/main.go` — every plugin answers `describe` with
  its product name and whether its harness CLI is installed.
- `internal/ui/ui.go` — `GET /version` and `GET /harnesses`; requests must
  use host `localhost` or `127.0.0.1`.
- `scripts/linux/Dockerfile`, `scripts/linux/run` — the Linux test container.
- `.github/workflows/check.yml` — `make check` on macOS and both Ubuntu
  runners; `release.yml` calls it before packaging.

## Decisions

### Makefile layout

The `Makefile` keeps the shared variables and targets (`binaries`, `check`,
`ui`, `screenshots`, `dev*`, `linux-*`, `web-*`) and includes one platform
file with that platform's packaging and installation:

```make
.DEFAULT_GOAL := bundle
ifeq ($(shell uname -s),Darwin)
include make/macos.mk
else
include make/linux.mk
endif
```

- `make/macos.mk` holds, unchanged, `APP`, `APPDIR`, `DESKTOP_EXE`,
  `SERVICE`, `MACOS`, `LSREGISTER`, and the `bundle`, icon, `build`, `release`,
  `install`, `place`, `quit-desktop`, and `install-service` rules, with its own
  `.PHONY` line.
- `make/linux.mk` holds `APP`, `bundle`, the icon rule, `build`, and
  `release`. The install and service task adds Linux `install` and
  `install-service` here.
- The `Makefile` keeps `BINDIR`, `APP_ID`, `APP_NAME`, `PORT`, `PLUGINS`,
  `ARCH`, and the shared packager command.

`ARCH` becomes `$(shell go env GOARCH | sed s/amd64/x64/)`, Electron's names
for the two architectures on both platforms (`uname -m` says `aarch64` on
Linux, which the packager rejects).

Both bundles run the same packager options, so the `Makefile` defines them
once:

```make
PACKAGER := bunx --bun electron-packager . "$(APP_NAME)" --arch=$(ARCH) \
	--no-asar --app-version=0.0.0 \
	--ignore='^/node_modules($$|/)' --ignore='^/bun\.lock$$' --ignore='\.test\.js$$' \
	--ignore='^/menubar\.svg$$' --ignore='\.desktop$$'
```

Each platform's `bundle` adds `--platform`, `--out`, and
`--executable-name` (macOS also `--app-bundle-id`). The `.desktop` ignore is
new and keeps the launcher file out of `resources/app` on both platforms.

### The Linux bundle

Checked in the container: `electron-packager . Hypercube --platform=linux
--arch=arm64 --executable-name=hypercube-desktop` writes
`Hypercube-linux-arm64/` with the `hypercube-desktop` ELF executable,
`chrome-sandbox`, Chromium's libraries and `.pak` files, `locales/`, and
`resources/app/`. It needs no tools beyond Bun and downloads Electron into
`~/.cache/electron`. The `bundle` rule moves that directory to `$(APP)`
(`bin/Hypercube`) and adds:

```
bin/Hypercube/
  hypercube-desktop                       Electron, from the packager
  hypercube
  hypercube-harness-{claude,opencode,codex,pi}
  resources/app/                          desktop/, from the packager
  resources/ui/                           internal/ui/dist
  resources/com.github.kkestell.hypercube.png
  resources/com.github.kkestell.hypercube.desktop
```

`resources/` holds what the app reads at run time, as `Contents/Resources`
does on macOS; the service installer goes there later. The executables sit at
the top so sibling discovery finds the plugins.

```make
bundle: ui bin/$(APP_ID).png
	cd desktop && ELECTRON_SKIP_BINARY_DOWNLOAD=1 bun install --frozen-lockfile
	rm -rf $(APP)
	mkdir -p $(dir $(APP))
	@tmp=$$(mktemp -d) && trap 'rm -rf "$$tmp"' EXIT && \
		(cd desktop && $(PACKAGER) --platform=linux --out="$$tmp" --executable-name=hypercube-desktop) && \
		mv "$$tmp"/* $(APP)
	cp -R internal/ui/dist $(APP)/resources/ui
	cp bin/$(APP_ID).png desktop/$(APP_ID).desktop $(APP)/resources/
	$(MAKE) binaries OUT=$(APP)

bin/$(APP_ID).png: cmd/hypercube/AppIcon.svg
	mkdir -p bin
	rsvg-convert -w 512 -h 512 -o $@ $<

build: bundle
	ln -sf Hypercube/hypercube bin/hypercube
	for p in $(PLUGINS); do ln -sf Hypercube/hypercube-harness-$$p bin/hypercube-harness-$$p; done

release:
	scripts/release
```

`rsvg-convert` renders `AppIcon.svg` at 512×512 in the container. The
directory keeps the macOS name, `Hypercube`, beside the `bin/hypercube` link.

### The desktop entry

One name, the app ID, ties the launcher, icon, and window together. The
source file is `desktop/com.github.kkestell.hypercube.desktop`:

```ini
[Desktop Entry]
Type=Application
Name=Hypercube
Exec=hypercube-desktop
Icon=com.github.kkestell.hypercube
StartupWMClass=com.github.kkestell.hypercube
Categories=Development;
```

`desktop/package.json` gets `"desktopName":
"com.github.kkestell.hypercube.desktop"`; Electron expects the file name with
its suffix and ignores it on macOS. Checked in the container with Electron
45.2.3 under Xvfb: with that `desktopName`, the window's X11 `WM_CLASS` is
`com.github.kkestell.hypercube`, which is what `StartupWMClass` names.
`Exec` and `Icon` name the executable and the icon theme entry; the install
task puts the bundle in place, writes `Exec`'s installed path, and installs
the PNG under that icon name.

### Release

`scripts/release` keeps its tag, HEAD, and clean-checkout checks, then runs
one function per platform, chosen by `go env GOOS`, and writes `SHA256SUMS`
for the archive the function names:

- `package_macos` — the current darwin/arm64 check, `make bundle
  APP=bin/release/Hypercube.app`, the identity check, `codesign --verify`, and
  the `ditto` ZIP `Hypercube-$tag-macos-arm64.zip`.
- `package_linux` — `make bundle APP=bin/release/Hypercube`, the identity
  check on `bin/release/Hypercube/hypercube`, and `tar -C bin/release -czf
  Hypercube-$tag-linux-$(go env GOARCH).tar.gz Hypercube`. Archive names use
  Go's architecture names, `amd64` and `arm64`, as the Linux plan does.

The identity check and `shasum -a 256` (present on Debian through Perl) are
shared. Any other GOOS fails with a message. The header comment says it
packages a beta for the machine it runs on. `release.yml` is unchanged; the
release task publishes the Linux tarballs.

### Linux tests and CI

`scripts/linux/test-bundle` (Bash, `set -euo pipefail`, header comment) runs
inside the container from the checkout copy:

1. `make build`.
2. Layout: `hypercube-desktop`, `hypercube`, and the four plugins are
   executable files in `bin/Hypercube`; `readelf -h` reports the desktop
   executable's machine as the host's (`AArch64` for `aarch64`, `X86-64` for
   `x86_64`); `resources/app/main.js` and `resources/ui/index.html` exist; the
   icon starts with the PNG signature; `desktop-file-validate` accepts the
   `.desktop` file; `desktopName` in `resources/app/package.json` equals the
   `.desktop` file's name; `bin/hypercube` and each `bin/hypercube-harness-*`
   resolve into `bin/Hypercube`.
3. `bin/Hypercube/hypercube version` prints a line starting `Hypercube `, and
   each plugin's `describe` prints JSON with its product name.
4. The backend: `bin/Hypercube/hypercube ui <port>` starts in the background
   with `XDG_CONFIG_HOME` and `XDG_STATE_HOME` in a temporary directory;
   the test polls `curl -fsS http://127.0.0.1:<port>/version` until it answers,
   failing at once with the backend's output if the backend exits first (the
   CI job's timeout bounds a hang), then checks that `GET /harnesses` lists `claude`,
   `opencode`, `codex`, and `pi`, which shows the backend found the plugins
   beside it. A trap stops the backend and removes the directory.

Each check prints what failed and exits non-zero. The image gains
`desktop-file-utils`; `readelf` comes with `gcc`'s binutils.

`make linux-test` runs `scripts/linux/run scripts/linux/test-bundle`. Later
Linux tests extend this target. `check.yml` gains a `linux-test` job on
`ubuntu-24.04` with checkout and `make linux-test`, timeout 30 minutes. It
needs no Go or Bun setup; the image has them. The Debian image's systemd boot
on GitHub's runner is unproven until this job runs; on failure, fix
`scripts/linux/run`'s container flags.

### What `make check` covers

`make check` is unchanged. Packaging stays separate from checks, as it is on
macOS; the bundle test covers Linux packaging, and the `desktopName` match is
checked on the built bundle.

## Test plan

- `scripts/linux/run scripts/linux/test-bundle` passes on the Mac (ARM64).
- The checks fail when broken: run once with a plugin removed from `PLUGINS`
  and once with a wrong `desktopName`, then restore.
- Release, as a one-off run through `scripts/linux/run bash -c '…'`: `git
  init`, commit everything, tag `v0.0.0-beta.1`, `make release`;
  `bin/release/` holds `Hypercube-v0.0.0-beta.1-linux-arm64.tar.gz` and
  `SHA256SUMS`, `shasum -a 256 -c` passes, and the extracted
  `Hypercube/hypercube version` prints `Hypercube v0.0.0-beta.1 (<commit>)`.
- `scripts/linux/run` (`make check`) still passes.
- macOS: `make bundle` and `make build` on the Mac, then compare the new
  `bin/Hypercube.app` with one built from `main`: `diff -r` shows only
  `desktopName` in `Contents/Resources/app/package.json` and the build
  identity, and `codesign --verify --deep --strict` passes. `scripts/release`
  on a dirty checkout still stops at the clean-checkout check. Do not run
  `make install` or `make install-service`.
- The CI job runs on the next push; report its result.

## Implementation plan

1. Move the macOS rules and variables into `make/macos.mk`, add the include,
   `.DEFAULT_GOAL`, the shared `ARCH` and `PACKAGER`, and use `PACKAGER` in the
   macOS `bundle`. Build on the Mac and compare with `main`.
2. Add `desktop/com.github.kkestell.hypercube.desktop` and `desktopName`.
3. Write `make/linux.mk`.
4. Split `scripts/release` into the two platform functions.
5. Add `desktop-file-utils` to `scripts/linux/Dockerfile`, write
   `scripts/linux/test-bundle`, and add `linux-test` to the `Makefile`.
6. Add the `linux-test` job to `.github/workflows/check.yml`.
7. Update the documentation and run the test plan.
