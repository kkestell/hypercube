# Simplicity review of the whole repository

## Scope and coverage

This review covers the whole repository except `agents/`, read as the working
tree stood on 2026-11-01. The goal was to find code to remove: over-engineering,
handling for failures that have not happened, hard-to-follow code, duplication,
and dead code. Where a change to runtime behavior would remove a lot of code,
the review proposes it and says what the user would lose.

Six reviewers worked in parallel, each with one focus:

- the Go core: Opus
- the plugins and protocol: GPT Sol
- the browser UI: Sonnet
- architecture and runtime behavior: Fable
- tests and scripts: GLM
- dead code, using staticcheck, deadcode and grep: DeepSeek

The lead merged duplicate findings, checked each kept finding against the code,
and ranked the findings by how much complexity each removes.

No finding has been fixed. The fix label says whether the fix needs a decision
from the user (`Needs decision`) or none (`Trivial`). Line estimates are
approximate.

Gaps:

- Other sessions were editing the shared checkout during the review. Uncommitted
  files may differ from what was read, and in-progress work may already be
  addressing some findings (see F15).
- F7 depends on each harness accepting an HTTP MCP server with custom headers.
  The reviewer confirmed this from the harnesses' binaries and type
  definitions, not by running them.
- F11 depends on how the ACP SDK handles `$/cancel_request`. The reviewer
  confirmed that by reading the SDK's code, not by running it.

## F1. The browser terminal panel is the largest optional subsystem

Medium · Architecture · Needs decision · `internal/terminal/terminal.go:1`

The terminal panel opens a shell in the workspace folder. It is the largest
subsystem with its own lifecycle, and it is a convenience: the user already
runs a terminal. It consists of:

- the `terminal` package: pty processes, an output buffer, fan-out to
  subscribers, resizing
- the `/terminal` WebSocket route in `ui.go`
- `Runtime.Shell`, and the `Terminals` calls in Stop, Delete, Shutdown and
  stopIdleSessions
- about 95 lines of panel JavaScript in `index.html`, plus the panel CSS
- the `creack/pty` and `@xterm/*` dependencies, with a 470 KB
  `static/terminal.js` bundle and its build step

### Fix

Proposed: remove the panel and everything above. That removes about 620 lines
of Go and JavaScript, plus `terminal_test.go`, `TestTerminalSocket` and
`TestShellsEndWithTheirSession`. The user would lose the shell beside the
transcript. If the panel stays, F18 still applies.

## F2. Split panes in the worker tab area need a layout tree

Medium · Architecture · Needs decision · `internal/ui/static/tabs.js:1`

Splitting a pane requires several pieces:

- a layout tree, with move, prune and replace operations that take an edge
- split sashes
- detecting which edge a tab is dropped on
- a drop-zone overlay
- a global drop guard in `index.html:862-875`

Of the 256 lines in `tabs.js`, about 110 would remain with a single tab strip.
That strip would keep drag to reorder, close and arrow-key navigation.

### Fix

Proposed: replace the splits with one tab strip. That removes about 240 lines,
counting `tabs.test.js` and the `.transcript-split` and `[data-drop]` CSS. The
user would lose viewing two workers side by side, which `docs/usage.md`
documents.

## F3. Four plugins copy the same test helpers

Medium · Simplicity · Trivial · `plugins/claude/main_test.go:76`

All four plugin test files define the same helpers:

- a fixture loader
- a transcript reducer that replaces or appends by item ID
- a state collector

Claude and Pi also share a verbatim connection driver of about 75 lines:
`connect`, `send`, `until` and `replyTo` (`claude/main_test.go:504-578` and
`pi/main_test.go:568-639` differ only in comments and one scanner check). Their
fixture splitter `until` is also copied (`claude:63-72`, `pi:85-94`).

### Fix

Proposed: one small test-helper package under `plugins/internal`. Each plugin
keeps its own process stand-in. This saves about 180 lines net.

## F4. Four plugins copy the same process lifecycle

Medium · Simplicity · Needs decision · `plugins/claude/main.go:85`

Each plugin has its own copy of the same steps, differing mainly in the binary
name:

- find the harness binary
- start the process with stdin and stdout pipes
- send stderr to a `plugin.Tail` and set `WaitDelay`
- a goroutine that reports "<name> exited: err: tail"
- `stop()`: close stdin, wait, then kill
- the error counter, `send`, `idle()` and `serve()`

The copies are in `claude/main.go:85-175`, `codex/main.go:88-135,236-258`,
`opencode/main.go:112-152,318-335` and `pi/main.go:117-173,206-220`. Codex and
OpenCode already share `plugin.Tail` and `plugin.RPC`, so this is the remaining
copied code.

### Fix

Proposed: one `plugin.Process` type (start, done, reason, stop) used by all
four plugins. This saves about 150 lines with no change in behavior. The type's
shape is a design choice, so it needs a decision.

## F5. Codex elicitation forms have a full form renderer

Medium · Architecture · Needs decision · `plugins/codex/requests.go:235`

`elicitationRequest` turns an MCP server's form into one attention request per
field. To do that it parses a JSON schema into fields and has value parsers for
booleans, numbers, strings and arrays. None of the MCP servers the agents use
sends form elicitations; Hypercube's own server sends none. Codex asks for
approval of MCP tools with message-only elicitations, which are handled
separately.

### Fix

Proposed: keep the message-only Accept/Decline request. Treat form and URL
elicitations like other unsupported requests, with an error item and a cancel.
This removes about 110 lines, plus the 34-line `TestElicitationForm` and a
sentence in `docs/harness-support.md`.

## F6. The empty state draws a WebGL tesseract

Medium · Architecture · Needs decision · `internal/ui/static/hypercube.js:1`

When no session is selected, a 139-line WebGL animation plays. It has no use
beyond decoration.

### Fix

Proposed: delete `hypercube.js`, its canvas, its script tag, and its two call
sites in `index.html` (about 145 lines). The empty state becomes a plain pane.
This is a branding decision.

## F7. The `hypercube mcp` bridge adds a process per agent

Medium · Architecture · Needs decision · `internal/mcp/mcp.go:113`

Each agent's harness starts `hypercube mcp`, which forwards MCP messages from
stdio to the app's `/mcp` route over HTTP. To pass the app's origin check, it
sets the app's own address as the request's `Origin`. Supporting it takes:

- the forwarding loop in `Bridge`, the `identity` transport and `nopCloser`
- the `mcp` subcommand
- the `HYPERCUBE_URL` and `HYPERCUBE_AGENT_ID` environment variables
- a bridge process for every running agent

All four harnesses accept an HTTP MCP server with custom headers:

- Claude Code: `type: http` with `headers`
- Codex: `http_headers`
- OpenCode: `McpServerHttp.Headers` over ACP
- Pi: `McpHttpServerConfig.headers`

### Fix

Proposed: each plugin configures `/mcp` directly over HTTP, sending the agent
header. `localOnly` would accept `/mcp` requests that carry the agent header
and no `Origin`; browsers always send `Origin` on cross-site POSTs. This removes
about 90 lines of Go and one process per agent, and the change is invisible to
the user. Each harness should be checked live first (see Gaps).

## F8. TestTeams repeats runtime tests

Medium · Testing · Trivial · `cmd/hypercube/integration_test.go:325`

`TestTeams` checks again what runtime tests already check:

- refusing a dirty worktree (325-355), also in `TestWorkerLifecycle` and
  `TestDelete`
- steering, routing failures and relaunching (388-408), also in three runtime
  tests
- holding queued messages across a stop and restart (410-455), also in
  `TestRestoredSessionHoldsMessagesUntilThePrompt`
- the restore checks (457-476), also in `TestAppProcess`

### Fix

Proposed: keep in TestTeams only what is visible at that level:

- HTTP action codes
- MCP tools through `/mcp`
- separation between sessions
- worktree and branch separation
- the `/state` snapshot
- adding and deleting workspaces

Reduce the repeated checks to one-line sanity checks. This removes about 120
lines.

## F9. Automatic relaunch after a plugin exits

Medium · Architecture · Needs decision · `internal/session/runtime.go:330`

When a plugin process ends, `ended` relaunches it up to `maxQuickExits` times.
That needs:

- the `quickExit` and `maxQuickExits` constants, plus `live.quick` and
  `live.launched`
- the `quick` parameter of `register`
- a relaunch branch and goroutine that loop from `ended` to `launch` and back

The user's service log and database show no relaunch actually happening. The
only logged launch failures are failed resumes ("No conversation found"), which
a relaunch does not fix. The behavior is documented in `docs/architecture.md`
and `docs/usage.md`.

### Fix

Proposed: `ended` records the exit, marks the agent exited, and stops. This
removes about 30 lines of code, the tests `TestRelaunchAfterTheProcessEnds` and
`TestAgentThatKeepsEndingStaysEnded` (about 50 lines), and the relaunch
paragraphs in the docs. The user would lose recovery from a crashed harness:
the agent stays exited until the session is stopped and started again, and
messages for it wait until then.

## F10. The UI learns of changes through two mechanisms

Medium · Architecture · Trivial · `internal/store/store.go:211`

`DB.Watch` checks SQLite's `PRAGMA data_version` every 250 ms on its own
connection, to learn of commits made by the app itself.
`docs/architecture.md:10` says the app is the only process that writes the
database. Transcript changes already arrive through the runtime's `changed`
channel, so `ui.go:64-80` runs two goroutines to learn about one thing.

### Fix

Proposed: `DB.Tx` signals after each commit, using the same pattern as
`Runtime.Changes`, and the UI waits on one signal. This removes about 50 lines
and the polling goroutine, and the sidebar no longer lags by 250 ms.
`TestTeams` queues a message through its own `store.Open`
(`integration_test.go:430`), so it would need to use the app's database handle.

## F11. OpenCode has its own ordering reader instead of plugin.RPC

Medium · Simplicity · Needs decision · `plugins/opencode/main.go:176`

The ACP SDK handles incoming requests concurrently. To keep them in order,
OpenCode wraps the connection in a custom reader. The reader has a `taken`
channel, decodes each message before the SDK sees it, keeps a partial line and
error, and waits for the handler to take each message.

`plugin.RPC` already handles messages one at a time in arrival order, and
`TestHandlerOrder` checks this.

### Fix

Proposed: use `plugin.RPC` for OpenCode and keep the ACP data types. This
removes about 35 to 50 lines of production code and part of
`TestDroppedMessageDoesNotBlock`. The trade-offs:

- The SDK's handling of `$/cancel_request` would be lost. Explicit
  `session/cancel` on interrupt remains.
- Malformed messages would produce `plugin.RPC`'s errors instead of the SDK's.

One reviewer judged the net gain unclear, so this ranks last among the Medium
findings.

## F12. Three packages build the same test world

`newFixture` in `runtime_test.go:32-79`, `newApp` in `ui_test.go:305-348` and

## F13. The `Idle` callback after start repeats the core's own transition

Low · API design · Trivial · `plugins/internal/plugin/serve.go:74`

After a successful start reply, `Serve` calls `Agent.Idle()`. Each of the four
implementations only emits an Idle state and the conversation ID again.
`Runtime.launch` (`runtime.go:261-267`) already marks the agent Idle on that
same reply. Codex and OpenCode already emit new conversation IDs when they
connect.

### Fix

Proposed: remove `Idle` from the `Agent` interface, the branch in `Serve`, and
the four methods, plus the test waits for that event. This removes about 40
lines with no visible change.

## F14. The plugin client kills a plugin over a stray reply

Low · Architecture · Needs decision · `internal/harness/harness.go:134`

`Client.read` ends the connection when a reply's ID matches no open request. To
keep that rule safe, `Do` leaves timed-out requests in `pending` forever, so a
late reply still matches. The plugins are first-party, and a stray reply is
harmless.

`Do` also waits up to a second after a failed write so it can return the
plugin's exit reason instead of the write error (`harness.go:175-183`). Later
calls return that reason anyway.

### Fix

Proposed:

- Ignore replies with unknown IDs, and delete a pending entry when its context
  ends.
- Return the write error directly.
- Delete the `!stray` stand-in, its subtest, and `TestLateReplyIsKnown`.

This removes about 45 lines, and `pending` stops growing. A plugin that sends a
stray reply would keep running.

## F18. Terminal exit codes, reconnects and the closed flag

Low · Simplicity · Needs decision · `internal/ui/ui.go:458`

This finding applies only if F1 is rejected. The terminal has three pieces of
bookkeeping:

- The server sends `{"exit":n}`, using `Done` and `ExitCode`. The page uses that
  message only to tell an exit from a dropped connection.
- After a drop, the page reconnects in a loop, using `connected`, `exited` and a
  `setTimeout` (`index.html:736-757`).
- `terminal.Set` refuses new shells after `Close`, using `closed` and
  `errClosed` (`terminal.go:33,48,66-68,109`). A shell opened during shutdown
  gets SIGHUP when the app exits anyway.

### Fix

Proposed: when the socket closes, close the panel; opening it again reattaches.
Also remove `ExitCode`, `Done`, the exit message, the `closed` flag and the
"RefusesNew" check. This removes about 45 lines. A dropped socket would close
the panel instead of reconnecting.

## F19. A failed AddWorker launch is undone instead of reported

Low · Architecture · Needs decision · `internal/session/session.go:382`

When a worker fails to launch, `AddWorker` undoes the add. It removes the live
launch, the worktree and the agent row, and builds two compound error messages
for when the cleanup itself fails. A failed session start is handled the
opposite way: `r.failed` keeps the agent, marks it exited, and writes the error
into its transcript.

### Fix

Proposed: on failure, call `r.failed(l, err)` and return the error. The lead
removes the worker with `remove_agent`, which already removes the worktree and
branch. This removes about 25 lines. A worker that fails to start would stay
listed as exited until it is removed.

## F20. Panel toggles, sash dragging and tab keys are written more than once

The UI repeats three pieces of interaction code:

  aria state and icon class in nearly the same way (`index.html:776-807`).
- Sash dragging is written twice, with the same 0.15 to 0.85 limits:
  `tabs.js:178-193` and `index.html` `drag()` at 833-853.
- Arrow, Home and End key handling for tab lists is also written twice:
  `tabs.js:205-219` and `index.html:818-831`.

### Fix

Proposed: one `toggle` function and one function each for dragging and tab
keys. This removes about 40 lines. F2 and F15 would remove most of this code
anyway.

## F22. Session activity has its own table

Low · Simplicity · Trivial · `internal/store/store.go:134`

Session activity is stored in a separate table, read through a `COALESCE`
subquery. The table exists only so that `SaveSession` does not overwrite the
activity time. Leaving the column out of `SaveSession`'s `UPDATE` does the
same.

### Fix

Proposed: add a `last_active` column on `sessions`. Fold `Input`'s separate
activity transaction (`runtime.go:611`) and `TouchSession` in `start`
(`session.go:118`) into their neighboring transactions. This removes about 12
lines and one table.

## F24. Transcripts are deduplicated twice

Low · Simplicity · Trivial · `internal/ui/transcript.js:261`

The server already sends only items whose bytes changed (`ui.go` sendTranscript
and `sentItems`), yet the client also compares each item with
`JSON.stringify(item)` against `r.json`. On the server, `sentItems` keeps a map
alongside the ordered list. A mismatched ID or a shorter list already forces a
reset, so comparing by index is enough (`ui.go:135-179`).

### Fix

Proposed:

- Remove the client comparison and its "unchanged" test check.
- Replace `sentItems` with a slice of ID and data pairs, compared by index.

This removes about 15 lines.

## F25. Unused fields, parameters and wrappers

Low · Simplicity · Trivial · `internal/harness/protocol.go:69`

Each item below was confirmed unused, or a thin wrapper, by grep, staticcheck
or deadcode:

- `StartArgs.Role` (`protocol.go:69`, set at `runtime.go:214`): no plugin reads
  it. The role already reaches the model through `report.Instructions`.
  `docs/harness-support.md` lists the field, so the docs change with it.
- `agent.dir` and `agent.model` in OpenCode (`opencode/main.go:67-68,169`) are
  set and never read.
- `ShownAgent.Dir` (`store.go:487,527`) is sent in every snapshot, and no
  browser code reads it.
- `RPC.Err` (`rpc.go:116`) is used only by a test in the same package.
- `pictures(doc, images, className)` (`transcript.js:100`) is always passed
  `[]`.
- `workspace.At` has a `base` parameter, and its only caller passes `"/"`
  (`session.go:23`).
- `Runtime.detach` only wraps `detachLocked` for its single caller.
- `Tx.Lead` only wraps `Find`.
- `harness.Spec` exists only to be embedded in `Profile`.
- In `mcp.go:84`, `if len(profiles) > 0` guards a loop that needs no guard.
- `report.Format` takes a slice, but it is only called with `queued[:1]`, after
  which `runtime.next` looks up the sender a second time
  (`report.go:79-89`, `runtime.go:560-563`).

### Fix

Proposed: delete each item, or inline it into its caller. For `report.Format`,
take one message and return its text with the sender's address. This removes
about 45 lines.

## F27. CheckImages computes decoded sizes before decoding

Low · Readability · Trivial · `internal/harness/image.go:26`

The size limit is checked before decoding, using a calculation that subtracts
base64 padding. `maxInput` (16 MiB) already limits the request body, so
decoding first costs nothing extra.

### Fix

Proposed: decode, then add `len(data)` to the total. Also remove the
padded-limit test cases (`image_test.go:15,30`).

## F28. The idle-stop check reads launch flags that cannot matter

Low · Simplicity · Trivial · `internal/session/inactivity.go:53`

The idle-stop check reads `l.starting || l.delivering` as well as
`Activity == Busy`. A start touches the session and has a one-minute timeout,
and a delivery has a 30-second timeout. The idle timeout is ten minutes, so
neither flag can change the result.

### Fix

Proposed: check `a.Activity == store.Busy` only. The idle-stop check would then
read no runtime state inside the database read.

`.hypercube/` is in the local Git excludes, so an empty
`.hypercube/<session>/` is invisible to Git.

### Fix

Proposed: remove the loop (about 8 lines). Empty directories would remain under
`.hypercube/`.

## F30. Runtime tests check internals and repeat a condition

Low · Testing · Trivial · `internal/session/runtime_test.go:358`

- At `runtime_test.go:358-364`, the inner `if` checks again a condition the
  outer `if` already established.
- At `:584` and `:631`, the tests check `f.rt.live`, which the `Activity`
  checks beside them already cover.

### Fix

Proposed: reduce the first to `if join != A && join != B`, and delete the two

## Checks run

- Read every Go, JavaScript, HTML and CSS file in scope, and traced callers with
  grep.
- staticcheck U1000, with and without tests, and whole-program `deadcode`.
- Read-only queries of the user's database and service log, used as evidence for
  F9, and to keep non-Git workspaces, which the user has.
- The lead checked these against the code: F3, F7, F9, F10, F13, F14, F15, F16,
  F19, F21, F25, F26, F27 and F30.

## Verdict

The code is generally lean. Most of the removable complexity sits in a few
features, not scattered across the code.

- F1, F2, F6 and F7 remove the most code, but each changes or drops something
  the user can see or relies on, so each needs a decision.
- With no change in behavior, F3, F4, F8, F10 and F13 remove the most, about 560
  lines together, mostly duplication in plugins and tests.
- F5, F9 and F14 remove handling for failures with no evidence that they occur.
- The Low findings are small and independent, and can be done in any order.
