# Holder executable plan assessment

## Scope and coverage

Parent assessment of [plan 009](../plans/2026-11-07-009-holder-executable.md)
against holder startup and inherited descriptors, holder command dispatch,
the test dispatch helper, agent launches, terminal creation and adoption, and
the backend's executable discovery.

## Summary

No findings. Supplying the holder executable through the existing
`session.Programs` boundary removes the requirement that every caller also
implement a holder command. A separate command reuses `hold.Main` and keeps
process ownership, descriptors, sockets, environment, and retained output in
the existing implementation. Existing holders still attach without an
executable path.

Keeping only the current embedded command would preserve the caller coupling
and test-binary dispatch that this plan addresses. Building the real holder
in test setup exercises the intended command boundary without adding a
second holder implementation. The legacy command serves the concrete bundle
replacement window in which an older backend can still launch a holder.

## Checks run

Inspected the plan and current holder, holder test setup, harness client,
terminal creation and adoption, and backend executable discovery. No code
checks were needed for this assessment.

## Verdict

Proceed within plan 009. Packaging remains in plan 011; tests build the
holder explicitly until then. The intermediate change is not ready to
install by itself.
