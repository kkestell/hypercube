## F1. `release` was defined identically in both platform files

Low · Clarity · Fixed · `Makefile:39`

`make/macos.mk` and `make/linux.mk` each defined `release: scripts/release`
with the same comment wording, though the rule is not platform-specific;
`scripts/release` chooses the platform.

### Evidence

Read both files.

### Resolution

`release` is a shared target in the `Makefile`, listed in its `.PHONY` line.
`make -n release` prints `scripts/release` on macOS and in the container.

## F2. `test-bundle` cleanup did not wait for the backend to stop

Low · Correctness · Fixed · `scripts/linux/test-bundle:58`

The exit trap sent SIGTERM to the backend and removed its state directory at
once. A backend still writing state could race the `rm -rf`, and under
`set -e` a failed `rm` in the trap changes the script's exit status.

### Evidence

Traced the trap; not reproduced.

### Resolution

The trap waits for the backend after killing it, then removes the directory.

## F3. The guide said `make` creates `bin/hypercube`

Low · Documentation · Fixed · `agents/development.md:205`

The edited paragraph said to run `make` and use `bin/hypercube`. `make` runs
`bundle`; only `build` links `bin/hypercube`, on both platforms.

### Evidence

Read `make/macos.mk` and `make/linux.mk`: the links are in `build`.

### Resolution

The paragraph says `make build`.

## F4. The unproven Linux job now also gates releases

Low · Process · Open · `.github/workflows/check.yml:34`

`release.yml` calls `check.yml`, so the new `linux-test` job runs before every
macOS release. Until the job has passed once on GitHub's runner, a container
boot problem there would block releases. This is the intended end state; the
open part is proving the job on the next push before tagging a release.

### Evidence

The plan states `release.yml` calls `check.yml`; the job has not run.

### Resolution

Open. Push the branch and confirm the job passes before the next release tag.
