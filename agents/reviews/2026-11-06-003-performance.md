# End-user performance review

2026-11-06 · baseline `fa062f44b159` and this uncommitted worktree · Apple M4, macOS, Go 1.27.3, Bun 1.4.2

## Summary

GPT workers examined the browser, backend, and agent/terminal paths. A
follow-up reproduced the slow file tree: restoring 410 expanded folders
blanked it for about 350 ms, even with an immediate Git response. Session
search took about 220 ms per query on the original 199-session database.
Subsequent isolated measurements covered 20 live stand-in sessions, a shown
Electron session switch, a dirty 5,000-file tree, and a 40 MB transcript.
The five leading everyday issues now have fixes in this worktree. Their
measured outcomes and limits appear below.

The rankings weigh delay, frequency, and confidence at the original checkout.
They are not browser paint-time measurements.

| Rank | Impact | Finding | Evidence |
| --- | --- | --- | --- |
| 1 | High, observed | Switching sessions clears and reloads the file tree, waiting for every expanded folder | 411 folder requests; 3,041 rows appeared after 349–360 ms in a hidden browser; immediate Git response did not improve it |
| 2 | High, observed | Session search scans saved transcript JSON for every query | 212–244 ms warm HTTP requests on the running app; first observed request 1.10 s |
| 3 | Medium to high, observed | File content search scans the repository per keystroke | 61–67 ms warm on this checkout; 210–244 ms in a 5,100-file fixture |
| 4 | Medium, workload dependent | Near-limit source files highlight synchronously on the browser thread | 140–187 ms warm, 339 ms first highlight in an isolated Bun run; 255 KB source produced 29.9 million HTML characters |
| 5 | Medium, recurring | Visible Files and diff views rerun Git work every second | Changes: 44–50 ms on this checkout, 94–100 ms in a 5,000-tracked-file fixture |
| 6 | Severe stress case | Selecting or reconnecting reloads and renders the whole transcript | A 40 MB expanded activity took 3.40 s to stable DOM and sampled renderer memory exceeded 1.1 GiB; the user chose this as a stress test, not a target for the current fixes |
| 7 | Low, fixed delay | Polling and batching delay individual terminal and transcript updates | Isolated terminal holder echo: 13.0 ms median, 25.0 ms p95; transcript batch window is 50 ms |

## Fixes and measured outcomes

| Issue | Change in this worktree | Follow-up evidence |
| --- | --- | --- |
| File tree | Cache visited session listings, read visible folders in one batch, and apply one update; preserve missing/deleted folders and reject stale responses | With 410 expanded folders, one request took 12–30 ms during warm switches, versus 127–411 ms for the earlier sequential 411-request pass. First tree rows appeared in 182–224 ms in the new shown-window fixture. The older 349–360 ms result used a hidden window and a different tree shape, so this is directional, not a paired browser speedup. |
| Session search | Two partial SQLite expression indexes, latest matching sequence before reading text, and request cancellation | On an isolated current-database copy through Go SQLite, no-match median fell from 245 to 4.1 ms; common-term median from 281 to 6.3 ms (10 warm samples each). Full ordered results matched on tested terms. |
| File-content search | Search four files concurrently per ordered batch, retaining the result cap and previews | Mixed 5,100-file fixture: actual handler no-match median 173 ms, p95 229 ms, versus 294/300 ms in an earlier serial replica; early 1,000-line-cap searches stayed near 61 ms. CPU rose from about 297 to 450 ms per no-match request. The runs used different harnesses. |
| Source/diff highlighting | Move file and diff highlighting to a worker; send 160-line chunks; emit only needed token classes | Synthetic 255 KB Go source markup shrank from 29.9 to 8.6 million characters. In 10 warm shown-window openings, plain text appeared at 37.8 ms median; full highlighting finished at 987 ms median while the median largest frame gap was 44.7 ms (maximum 50.1 ms). An earlier three-run probe had one 317 ms gap, so rare stalls remain possible. |
| Git changes | One porcelain status call supplies branch and untracked paths; one diff supplies tracked status and counts | A dirty 5,000-file route took 54 ms median across 24 warm requests, but p95 was 120 ms and one 12-request run centered near 98 ms. The previous fixture measured 94–100 ms, so a sustained route speedup is not established. |

The same 20-session shown-window switch fixture had **453 ms mean stable DOM**
at baseline and **492 ms mean** with the new tree path, each over 20 warm
switches. Stability includes a required 250 ms quiet window. Separate runs
and system load prevent attributing the difference to the change; this
benchmark does **not** show a lower average click-to-stable-DOM time. It does
show far fewer tree requests and a tighter tail: warm switches started one or
two tree requests instead of six to twelve folder requests. With 410 expanded
folders, three steady refreshes finished tree plus Git responses in
91–97 ms, within the existing one-second poll period.

The indexed search added about 4.4 MB to a 130 MB transcript database and
took 293 ms to build once. Individual committed 4 KB searchable item inserts
rose from 81 to 128 µs median; replacements from 56 to 117 µs. The 40 MB
all-searchable stress fixture's indexed no-match and common-match medians
were 56 and 25 ms, versus 117 and 273 ms before indexing. Those costs
exclude concurrent agent work and browser rendering. No transcript
windowing or pagination was added: the user chose to use the 40 MB case as a
stress test while fixing everyday paths first.

## Baseline findings (before the fixes)

The following source paths identify the areas investigated; the behavior
described in this section was observed at checkout `fa062f44b159`, before
the changes above.

### 1. File tree on session switch

[Session attachment](../../internal/ui/web/sessions/selection.ts#L92) saves
which folders were expanded but [restores empty listings](../../internal/ui/web/sessions/view-state.ts#L18).
[FilesPanel](../../internal/ui/web/app/right-panel.tsx#L20) remounts for each
session. Its [mount effect](../../internal/ui/web/files/files-panel.tsx#L48)
requests the root and every remembered expanded folder, and its
[render gate](../../internal/ui/web/files/files-panel.tsx#L111) leaves the tree
blank until **all** those requests have finished. Each
[folder response](../../internal/ui/web/files/files.ts#L97) updates the store
while the tree is still hidden, so the panel does repeated work before its
first complete draw. Git changes load separately;
they can add status decorations later but do not gate the initial tree.
[PanelTabs](../../internal/ui/web/shared/panel-tabs.tsx#L18) keeps FilesPanel
mounted even when its tab is hidden, so the work also starts on switches when
the user is not viewing Files.

In a separate browser window using this checkout's installed backend, a switch
with no expanded folders showed 17 rows at about 30 ms. Restoring 174 expanded
folders requested 175 directories and showed 1,400 rows at 174 ms. Restoring
410 expanded folders requested 411 directories and showed 3,041 rows at
349–360 ms across two runs. In the latter runs, the last `/files` response
arrived by 90–104 ms; replacing `/changes` with an immediate empty response
still showed the tree at 360 ms. These are DOM mutation times in a hidden
Electron browser, not visible paint times. They reproduce the blank interval
and show that Git is not the main gate in this case. The user's roughly
one-second experience was not reproduced; larger or slower trees and a visible
window need direct profiling.

When the page and Files tab are visible,
[the poller](../../internal/ui/web/files/file-polling.ts#L19)
refreshes the root and every expanded folder **sequentially** each second,
then refreshes Git changes. A read-only sequential pass over 411 folders took
127–411 ms in three hidden-browser samples, before any store or DOM work. That
pass can overlap a session's initial load and can produce further updates as
files change. Preserve an already loaded tree across in-page session switches
and avoid gating the whole tree on every remembered folder; then measure the
visible switch and refresh sequence. Keep Git status separate from tree
availability.

### 2. Session search

[The query](../../internal/store/search.go#L13)
extracts JSON text from the transcript table in two branches, searches it with
`instr(lower(...))`, and ranks matches per session. The installed database has
199 sessions, 13,993 transcript entries, and 113.4 MiB of transcript JSON.
Five requests each for a one-letter match, a common-word match, and a no-match
query took 212–244 ms after warmup; nine earlier warm no-match requests took
220–229 ms. These are local HTTP times, so network delay is negligible.

[The search dialog](../../internal/ui/web/sidebar/session-search.tsx#L20)
starts a request and clears results whenever the query changes. It also shows
"No sessions found" while a request is pending. Browser aborts do not cancel
[the database transaction](../../internal/store/store.go#L190),
which uses `context.Background()`. This makes fast typing likely to spend work
on obsolete queries. Profile the query on representative state, then avoid
repeated full JSON scans. Verify typing and result latency after the change.

### 3. File content search

[The search panel](../../internal/ui/web/files/search-panel.tsx#L19)
requests a search for every query change. [The handler](../../internal/ui/search_files.go#L34)
enumerates candidate files, then opens and searches each file until the scan
finishes or it reaches 1,000 matching lines. A no-match request on the current
checkout took 61–67 ms warm and 121 ms first. In an isolated Git repository
with 5,000 tracked files and 100 untracked files, three benchmark runs measured
210–244 ms per no-match search. Cancellation is checked during enumeration and
between files, which limits obsolete work, but each completed query still
starts from the beginning. Reduce repeated scans during typing and measure on
larger real repositories before choosing a persistent index.

### 4. Source and diff highlighting

[FileView](../../internal/ui/web/files/file-view.tsx#L21)
loads the highlighter lazily, then calls it synchronously on the browser thread
for the entire file. The lazy bundle is 2.3 MB uncompressed. The server accepts
files up to [256 KiB](../../internal/ui/files.go#L18).
In an isolated Bun run, importing the highlighter took 124 ms; highlighting a
synthetic 4,000-line, 255 KB Go file took 339 ms first and 140–187 ms on five
warm runs. [Per-token HTML](../../internal/ui/web/files/highlight.ts#L59)
expanded that input to 29.9 million characters. Plain text appears first, but
the later highlight can pause interaction; browser layout and paint may add
more. [DiffView](../../internal/ui/web/changes/diff-view.tsx#L22)
highlights both complete sides separately. First profile this case in a visible
browser, then reduce main-thread work or the amount of markup for large files.

### 5. Git changes and diff polling

[The file poller](../../internal/ui/web/files/file-polling.ts#L19)
refreshes changes once per second while Files or a diff is visible, and then
refreshes each active diff in sequence. The changes route cost 44–50 ms per
request on this clean checkout and 94–100 ms in an isolated repository with
5,000 tracked files, 100 modified files, and 100 untracked files. A modified
diff cost 28–30 ms in that fixture. [Changes](../../internal/workspace/changes.go#L26)
runs several Git commands; the route also counts lines in untracked files.
Repeated work on unchanged repositories consumes time in every open page and
can delay refresh when several panes are open. The session-switch probe shows
that this Git call is not what keeps the initial tree blank. Reduce redundant
Git work and avoid transferring unchanged diffs. Keep the existing
one-second freshness behavior unless a measured tradeoff supports changing it.

### 6. Whole-transcript selection and updates

[Session selection](../../internal/ui/socket.go#L126)
loads and sends every saved item. [The runtime](../../internal/session/transcript.go#L60)
decodes them while holding its shared mutex. On the current app, selecting an
ended transcript of 242 items and 5.2 MB took 32–54 ms from WebSocket send to
receipt and JSON parse; one of 629 items and 0.58 MB took 20–28 ms. An isolated
backend benchmark took 12–13 ms to read and decode 10,000 short items. The
browser [renders every row](../../internal/ui/web/transcript/transcript.tsx#L70),
and [each update rebuilds order](../../internal/ui/web/transcript/transcripts.ts#L11)
and rows. A synthetic 50,000-item update spent 4.9 ms median in those data
transforms alone; this excludes React and layout. Current selection transfer
is measurable but not yet a proven user-visible stall. Profile a large real
session in a visible browser before introducing windowing or pagination.

### 7. Stream and terminal response floor

[Holder output](../../internal/hold/output.go#L26)
polls retained segments every 25 ms when idle. A real holder and PTY with a
`cat` stand-in returned 40 line echoes in 0.2–26.2 ms, with 13.0 ms median and
25.0 ms p95. The [data socket](../../internal/ui/socket.go#L18)
coalesces transcript changes for 50 ms. These are intentional throughput and
latency choices; the test excludes WebSocket, rendering, and model time to
first token. Optimize them after the larger measured search and file costs, if
end-to-end typing or streaming still feels delayed.

## Baseline and limits

### Combined scale scenarios

The follow-up fixtures deliberately separate live-agent load from browser
rendering. With 20 simultaneous stand-in sessions, sequentially starting them
all took 1.43 s. Their start-to-first-ack median was 63.6 ms and p95 was
74.6 ms (20 samples). In 50 rounds of 20 concurrent inputs, the selected
session's next item reached a local WebSocket in 71.7 ms median, 124.1 ms p95,
and 201.2 ms maximum. This includes the 50 ms stream batch but excludes
browser rendering and real model time.

In a shown Electron window backed by 20 scripted idle sessions, 5,000 tracked
files, 100 modified and 100 untracked files, five expanded folders, 2,618
visible file rows, and a 500-item, roughly 270 KB transcript, 20 warm session
switches averaged 138 ms to the first tree rows, 187 ms to the Git decoration
and last transcript marker, and **453 ms to stable DOM** (median 449 ms, p95
466 ms). Stable required the target markers, then 250 ms without relevant DOM
mutations and at least two animation frames; about 250 ms of the reported time
is deliberately a quiet window. The first switch was slower (618 ms stable).
This uses programmatic clicks, not physical input or paint timing; the 20
sessions were present but idle rather than producing concurrent output.

A single session with 40,000,000 ASCII text bytes approximates 10 million
tokens only under a four-bytes-per-token heuristic. Real tokenizer counts vary.
For 1,000 and 10,000 items containing that same total, backend transcript read
and JSON decode took 46.5 and 53.5 ms median respectively; separate JSON
marshal took 29.2 and 31.8 ms median. The Go benchmark process reached
304–338 MB peak RSS, excluding browser and holder processes. In the combined
Electron fixture with 500 large items, an activity left collapsed reached
stable DOM at 720 ms. Restoring it expanded took **3.40 s** to stable DOM; its
last marker appeared at 3.14 s, and sampled renderer working set climbed to
about **1.14 GiB**. These are one sample each, not a distribution. The large
expanded activity is a demonstrated browser bottleneck, while whole-transcript
transfer also remains an unbounded cost.

The search query was also tested on the 40 MB all-searchable fixture. Extracting
searchable text into its own table cut no-match scans from roughly 95–122 ms
to 62–67 ms, but the current window query still took roughly 330–500 ms when
every item matched. Selecting the latest matching sequence first and reading
only its text reduced that common-match case to roughly 34–37 ms. This query
shape matters independently of the index or storage choice.
The final fix uses partial expression indexes on the existing transcript
table; it does not maintain a second searchable-text table.

### Other baselines and limits

- A local Electron browser load reported 50 ms to `loadEventEnd`, 9–38 ms for
  five initial state WebSocket requests, a 71 KB state payload, and 199 sessions.
  The eager JavaScript files total about 1.1 MB uncompressed. The browser window
  did not expose paint timing, so these are not time-to-visible-content figures.
- Five empty-state backend starts reached `/version` in 643 ms once and
  10–27 ms thereafter. This does not represent restoration of active agents.
  [Restore](../../internal/session/restore.go#L101)
  rereads saved launch transcripts before HTTP service starts; its cost
  on an active installation was not measured.
- The three GPT workers used for this review reached the app's ready state
  0.18–0.67 s after creation and wrote their first text 2.9–3.7 s after
  creation. These are three concurrent launches, not a harness or model
  latency distribution; the app and model contributions to first text were
  not separately measured.
- A synthetic 1,000-session snapshot took 23 ms per build, and state is rebuilt
  per connected browser after durable writes. At the current 199-session
  volume, initial state delivery is smaller than the measured search cost.
- Enumerating 5,100 files for quick open or mentions took 60–77 ms in the
  synthetic repository. Ordinary folder listing and unchanged file reads were
  much cheaper, so these did not rank above content search.
- Native harness startup, model time to first token, full browser interaction
  paint, and contention under simultaneous users were not measured. The MCP
  bridge serializes calls, and launch holds a shared runtime mutex, but there
  is no evidence here that either is a common user-facing bottleneck. They are
  leads to measure if agent startup or concurrent tools remain slow.

## Measurement notes

Baseline live requests used the installed app at the baseline commit and
read-only `curl`/WebSocket calls. The file tree switch probe used a separate
Electron browser window with expanded folders in its own view state; that
window was hidden, so its interval poller did not run and paint was not timed.
The running database was counted with read-only SQLite queries. The workers'
Go benchmarks used temporary overlay files, temporary SQLite databases or Git
repositories, and warm filesystem
cache; no user workspace was stopped or modified. Initial highlighter and
transcript processing probes used Bun; the follow-up source and session-switch
measurements used a shown Electron window and a separate local backend.
The terminal probe used a temporary holder with a shell `cat` stand-in.
The baseline measurements were read-only. Follow-up changes were made only
in this session's worktree; the installed app and live state were not changed.

## Verification

`make check` passed after the code changes, including the browser build and
tests, Go vet, and Go race tests. An independent implementation review found
two tree error cases: a folder replaced by a file blocked a whole batch, and
a removed session folder left cached rows visible. Both were fixed and the
reviewer reran the isolated reproduction. The isolated development view
served HTTP 200; browser behavior was checked in shown Electron fixtures.
The changes remain uncommitted in this session's worktree.
