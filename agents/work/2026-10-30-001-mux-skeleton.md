# Mux skeleton and minimal working path

## Plan

`agents/plans/2026-10-30-001-mux-skeleton.md`

## Summary

The `mux/` module exists with its Makefile, and the top-level `make check` runs it. A server on `$XDG_STATE_HOME/mux/socket` starts on first use, `spawn` and `capture` work, and `mux attach` shows the pane and detaches on Ctrl-b d. The plan's goal is met.

## Departures from the plan

- The libghostty-vt build ran with the planned Zig flags and needed no fixes. The permission classifier denied me the build, so the lead ran it. The lead's run did not write the `.built` stamp; I created it with `touch`.
- `client.Conn.Send` takes a mutex. The attach client sends from two goroutines (input and resize), which the plan's "no concurrent use" note for `Conn` did not cover.

## Decisions

- `Server.ListenAndServe(path)` owns the directory, the already-running check, and stale-socket removal, so `mux server` only calls it.
- Output to an attached client comes only from its draw goroutine. On detach, the handler stops that goroutine before it writes `detached`, so no lock guards the connection.
- A resize or attach with a bad size returns the `Terminal.Resize` error. Nothing else validates it.
- In the stream, unknown request types are ignored.

## Checks run

- `make check` — passes (top-level, including `mux`).
- `make -C mux check` — vet, gofmt, and `go test -race` pass.

## Manual verification

The hand check ran in a Ghostty window under `expect`, because `mux attach` needs a terminal and `expect` could type into it. Build `bin/mux` with `make -C mux build`, set `XDG_STATE_HOME` to a scratch directory, and script this:

1. `mux spawn` prints `s1 w1 p1`.
2. `mux attach s1` on a 100 by 30 terminal draws the shell prompt with its colors.
3. Typing `stty size` shows `30 100`.
4. Ctrl-b d leaves the alternate screen, shows the cursor, and exits 0.

All four held. I stopped the server and deleted the scratch directory afterward.
