# Run the browser view as a login service

Builds on `2026-10-31-001-web-ui-only.md`.

## Goal

The user installs `hypercube ui` once as a macOS login service, so it runs in
the user's own login environment no matter who starts or restarts it. Agents
it launches no longer inherit the environment of whatever process started the
view, such as a Claude Code agent's shell. Two make targets replace the
installed build:

- `make reinstall-ui` installs the build and restarts only the view. Running
  sessions keep running.
- `make reinstall` waits until no agent is busy, then stops every running
  workspace, installs the build, restarts the view, and has the view start the
  workspaces again. Run inside Hypercube, it fails at once.

## Related code

- `Makefile` — `install` and `reinstall` targets.
- `scripts/reinstall` — refuses inside Hypercube, stops running workspaces,
  installs, and starts them again with `hypercube start`.
- `internal/harness/harness.go` — `Launch` copies the launching process's
  environment into the agent's pane. The view launches every session the user
  creates, so its environment becomes theirs.
- `internal/ui/ui.go` — `workspaceAction` starts a workspace from a picked
  folder; `localOnly` requires a matching `Origin` on commands;
  `TestActionsRejectBadRequests` covers bad actions.
- `internal/tmux/tmux.go` — `Activity` sets each agent pane's
  `@hypercube_busy`.

## Decisions

- **Service:** a launchd user agent with label
  `com.github.kkestell.hypercube`, defined once in the `Makefile` as
  `SERVICE` and passed to the scripts. Its property list in
  `~/Library/LaunchAgents/` runs `$SHELL -lic 'exec "$BINDIR/hypercube" ui'`
  with `RunAtLoad` and `KeepAlive`, logging to
  `~/Library/Logs/hypercube-ui.log`. launchd gives the service a clean
  environment, and the interactive login shell adds the user's PATH and
  credentials, which the user's shell files set in both `.zprofile` and
  `.zshrc`.
- **Install:** `make install-service` installs the build, writes the property
  list, and loads it with `launchctl bootstrap`, replacing a loaded copy with
  `launchctl bootout` first. It fails if another process already listens on
  port 4280, naming the command to stop it.
- **Busy:** an agent is busy when its pane's `@hypercube_busy` is set. That
  includes an agent waiting for approval, which is mid-turn. `scripts/reinstall`
  reads it with
  `tmux list-panes -a -f '#{@hypercube_busy}' -F '#{window_name}: #{@hypercube_label}'`,
  prints the list whenever it changes, and checks again every two seconds.
  No tmux server means nothing is busy.
- **Restarting workspaces:** `scripts/reinstall` starts them through the
  restarted view with
  `curl --fail-with-body --retry 30 --retry-connrefused -X POST -H 'Origin: http://localhost:4280' --url-query "dir=$dir" 'http://localhost:4280/workspace?action=start'`,
  so their agents get the service's environment. `workspaceAction` gains a
  `start` action that runs `hypercube start <dir>`; a missing `dir` is a bad
  request. `make reinstall` requires the service to be loaded and fails before
  stopping anything if it is not.
- **`reinstall-ui`** runs inside Hypercube too: it stops no agents. Running
  agents call the installed executable for their hooks, MCP server, and
  wake-ups, so they use the new build at once. It suits changes that leave
  those and the state format unchanged.

## Test plan

- `TestActionsRejectBadRequests`: `POST /workspace?action=start` without `dir`
  returns 400.
- Live, run by the user:
  - `make install-service` starts the view; `ps eww` on it shows the user's
    PATH and no `CLAUDE_CODE_*` variables; a session created in the browser
    shows no child-session warning. With a manually started view on port 4280,
    it fails and names the command to stop it.
  - `make reinstall-ui` reloads the page within seconds; every agent pane keeps
    its process ID.
  - `make reinstall` with a busy agent lists it and waits; once it is idle,
    workspaces stop, the build installs, the view restarts, and every workspace
    that was running starts again with its sessions. Inside Hypercube it fails
    before doing anything. Without the service loaded it fails before stopping
    anything.

## Implementation plan

1. `internal/ui/ui.go`: add the `start` action to `workspaceAction`; update its
   comment. Extend `TestActionsRejectBadRequests`.
2. `scripts/install-service` (new): write the property list and load it as
   decided, with the port check.
3. `scripts/reinstall`: keep the refusal inside Hypercube; check the service is
   loaded with `launchctl print gui/$(id -u)/$SERVICE`; wait while agents are
   busy; stop the running workspaces as now; install; restart the view with
   `launchctl kickstart -k`; start the stopped workspaces through the view.
   Update the header comment.
4. `Makefile`: add `SERVICE`; add `install-service` (after `install`) and
   `reinstall-ui` (after `install`, then `launchctl kickstart -k
   gui/$$(id -u)/$(SERVICE)`); pass `SERVICE` to `scripts/reinstall`; update
   `.PHONY`.
