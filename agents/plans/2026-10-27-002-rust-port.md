# Rust port

## Goal

Hypercube is rewritten in Rust. It supports two harnesses, Claude Code and Pi,
and draws its own panes: one `hypercube` process hosts every agent's pty and
Ghostty terminal and draws them into the user's terminal, using terminal code
taken from granite into this crate. Message delivery, worktrees, the state
file, and the MCP tools behave as they do now.

The first milestone is an MVP that runs a team end to end on a foundation
that later features extend without restructuring: a terminal layer with
dynamic panes and a caller-driven event loop, a host process with a control
socket, and direct ports of the store, workspace, harness, hook, and MCP code.

## Related code

Hypercube (Go, about 2,100 lines without tests):

- `cmd/hypercube/main.go`: CLI, `start`, `stop`, `delete`, `status`.
- `internal/tmux/tmux.go`: every tmux call. This package is what the terminal layer
  replaces.
- `internal/store/store.go`: the locked JSON state file.
- `internal/workspace/workspace.go`: checkout discovery, worktrees,
  `.worktreeinclude`, submodules, removal checks.
- `internal/harness/{config,harness}.go`, `pi.js`: configuration, launch
  commands, the Pi extension.
- `internal/mcp/mcp.go`: the stdio MCP server and its four tools.
- `internal/hook/hook.go`: hook events and the runtime facts.
- `internal/limits/limits.go`: Claude Code status line and status bar limits.

Granite (Rust, `~/src/granite`), a proof of concept. Its `src/mux.rs`,
`src/winch.rs`, `src/recording.rs`, round-trip and hold tests, and recordings
are now this crate's terminal layer:

- `src/mux.rs`: `Mux` and `Pane`. Each pane owns a libghostty-vt `Terminal`
  and a `Frame` that captures dirty rows; `Mux` routes host input to the
  focused pane, mirrors its input modes onto the host, draws chrome, and
  renders frames inside synchronized output. Mode 2026 holds, host color and
  grapheme queries, and focus events are handled here.
- `src/main.rs`: argument parsing, `forkpty`, host raw mode and alternate
  screen, the host query round trip, and the `poll` event loop with frame
  pacing (16 ms) and hold expiry.
- `src/winch.rs`: SIGWINCH through a self-pipe.
- `tests/roundtrip.rs`, `tests/live.rs`, `tests/holds.rs`: renderer
  round trips, real-pty tests with a scripted child, hold behavior.

The terminal layer's current shape that the port must change:

- `Mux::new` takes 1 to 3 labels and asserts that; `layout()` hardcodes the
  three arrangements; panes are addressed by index; the title callback
  captures the pane index.
- Spawning and the event loop are in granite's `main.rs`, which was not
  copied. Phase 0 brings that code in as the runtime, with the live tests and
  scripted child from granite's `tests/live.rs` and
  `src/bin/granite-test-child.rs`.
- `forkpty` masters are inherited by later children, which the child closes
  by hand; nothing sets `FD_CLOEXEC`.
- Everything is single-threaded with `Rc`/`RefCell`, and libghostty is not
  shared across threads. The host must stay a single-threaded `poll` loop.

libghostty-rs already exposes what several features need: a key encoder that
reads a terminal's modes (`ghostty_key_encoder_setopt_from_terminal`), paste
encoding, `scroll_viewport` and `scrollback_rows`, `on_clipboard_write`, and
`on_pwd_changed`. It has no callback for desktop notifications (OSC 9 and
OSC 777).

## Decisions

### The host process

`hypercube` becomes the session: a foreground process that owns the host
terminal, every agent's pty and Ghostty terminal, and the control socket. It
ends when the user stops it, when every agent has exited, or when its
terminal closes. This keeps the "no daemon" principle: the host is a
long-lived foreground process like a harness, and everything else stays
short-lived. Persistence across restarts comes, as now, from saved harness
sessions and the queued messages in the state file.

Detach and attach (phase 4) fit this design later: the host moves to the
background and a client passes its terminal's file descriptor over the
control socket with `SCM_RIGHTS`, so the host keeps writing frames directly
to the user's terminal and the client only forwards SIGWINCH and waits.
Nothing in the MVP depends on the host's stdio being its own, beyond the
`Runtime` taking the host input and output descriptors as parameters.

### Liveness and control

- **Host lock:** the host holds an exclusive, non-blocking `flock` on
  `<workspace>.host.lock` for its lifetime. A workspace is running when that
  lock is held. The kernel releases it if the host crashes, so there is no
  stale-pid problem. `status`, `stop`, and a second `hypercube` check it.
- **Control socket:** the host listens on a Unix socket next to the state
  file. Each connection carries one JSON request line and gets one JSON reply
  line. Requests:
  - `launch {agent, prompt}`: load the agent from the state, build its
    command, spawn it in a new pane, and lay the panes out again.
  - `close {agent}`: hang up the pane's process group, close the pane, and
    lay out again.
  - `nudge {agent}`: type the nudge into the pane and schedule Enter.
  - `stop`: end the session.
- Only the MCP server (create, remove, send) and the CLI (`stop`) talk to the
  host. Hook processes touch only the state file, as now.
- The host builds launch commands from the agent record, so the request
  carries an agent ID and the command builder has one caller. The MCP server
  still creates the worktree and the agent record before asking for the
  launch, and rolls both back if the launch fails, as `createAgent` does now.
- The socket path is `<state dir>/<hash>.sock` with a short hash of the
  workspace name, because macOS limits socket paths to 104 bytes. The host
  fails with a clear error if the path is still too long. A leftover socket
  file is removed when the host acquires the host lock.
- The MCP server and CLI find the socket from `HYPERCUBE_STATE`, so the Pi
  extension and the MCP server environment no longer carry `TMUX`.

### Terminal layer

The terminal layer (`src/lib.rs`: `mux`, `winch`, `recording`, and the
runtime) owns terminals, ptys, rendering, input routing, and the host
terminal; the rest of the crate owns layout, chrome, and everything about
agents. The crate has no dependency on granite. Changes, in the order they
land:

1. **Pane identity.** `PaneId` is a stable integer. `Mux` stores panes with
   their IDs, focus is a `PaneId`, and terminal callbacks capture the ID.
2. **Dynamic panes.** `Mux::add_pane` and `Mux::remove_pane`; no pane count
   limit.
3. **Caller layout and chrome.** The caller assigns each pane a rectangle
   (`Mux::set_layout(&[(PaneId, Rect)])`) and draws chrome through a
   `Chrome` trait that receives a read-only view of the panes (label,
   rectangle, focused, exit status) and the host size. Setting a layout
   resizes each terminal and pty and repaints. The round-trip and hold tests
   use a one-pane layout and guard the refactor.
4. **Spawning.** `Pty::spawn(argv, cwd, env, size)` with
   `TERM=xterm-256color` and `COLORTERM=truecolor`, masters marked
   `FD_CLOEXEC`, the child in its own session. `Mux::close_pane` sends SIGHUP
   to the process group, closes the master, and the runtime reaps with
   `WNOHANG` so a slow exit never blocks the loop.
5. **Runtime with caller events.** Granite's `main.rs` loop becomes
   `Runtime`, which owns host setup and restore, the host query round trip,
   SIGWINCH, frame pacing, hold expiry, pty reads, and input routing. The
   caller drives it step by step:
   `runtime.wait(&mut mux, extra_fds, deadline) -> Vec<Event>` with
   `Event::Ready(fd)`, `Event::PaneExited(id, status)`, `Event::Resized`,
   and `Event::Deadline`. A step API avoids callbacks that need `&mut Mux`
   while the runtime holds it.
6. **Programmatic input.** `Mux::send_text(id, &str)` writes text as typed
   keys, and `Mux::send_key(id, Key::Enter)` encodes the key with Ghostty's
   key encoder configured from the pane's terminal, so Enter is right under
   Kitty keyboard flags.
7. **Chrome invalidation.** `Mux::invalidate_chrome()` for the caller's own
   changes, such as the status bar.

The crate builds libghostty-vt from its own `vendor/ghostty` submodule and
its own Zig in `.toolchain`, which `make` downloads when missing.

### Hypercube crate

One binary, `hypercube`, synchronous code, no async runtime. Dependencies:
`libghostty-vt`, `libc`, `serde`, `serde_json`. Modules mirror the Go packages:

- `store`: state types with serde, `update(path, |state| ...)` under `flock`,
  atomic write, `load`, `delete`, IDs. Unknown fields are ignored, so state
  files written by the Go version load.
- `config`: configuration loading and validation.
- `workspace`: a direct port, shelling out to `git` and `cp -c`.
- `harness`: `command(agent, state_path, prompt) -> Launch {argv, env, cwd}`
  for Claude Code and Pi, the embedded Pi extension, labels.
- `hook`: events, facts, message formatting.
- `mcp`: the JSON-RPC loop and tools; `control::request` for host calls.
- `control`: the socket protocol types, client, and the path rule.
- `host`: the session: host lock, socket listener, the `Mux` and
  `Runtime`, the main-vertical layout, the chrome, agent-to-pane map, nudge
  timers, teardown.
- `main`: argument dispatch and the `status`, `stop`, `delete` commands.

Functions return `Result<T, Box<dyn Error>>` with context in the message, as
the terminal layer does; tool errors reach the model as text, as now.

### Layout and chrome

The orchestrator's pane is the left 40% of the columns; a one-column heavy
vertical rule follows; workers split the remaining columns with equal heights.
Each pane has a one-row label above it, drawn as a heavy horizontal rule in
blue (`#0087ff`, tmux `colour33`) with the label in black on light blue
(`#87d7ff`, `colour117`), bold when focused. The bottom row is the status
bar, black on light blue, with the checkout path. A pane needs at least one
label row and one content row; a layout that cannot fit every pane returns an
error, which fails the launch. Exited panes keep their place and show
"exited N" after the label.

### Teardown

On `stop`, on input EOF from the host terminal, or when every pane has
exited, the host sends SIGHUP to each live pane's process group, gives them
up to two seconds, sends SIGKILL to the rest, restores the host terminal,
removes the socket, and releases the host lock. A harness ended by SIGHUP
behaves as it does under `tmux kill-session`.

### Repository

The Go code is in `v1/`, as reference material, and the Rust crate is at the
root. New code and docs do not refer to `v1/` or its predecessors. The state directory and format stay the same throughout, so
either version can run a workspace.

## MVP slice

The MVP proves the architecture end to end and contains everything later
phases build on. It is done when a user can run `hypercube` in a checkout,
the Claude Code orchestrator creates Pi and Claude Code workers in worktrees,
messages flow both ways including nudges to idle agents, workers are
removed after merging, and `stop`, `status`, `delete`, and a restart that
resumes sessions all work.

In the MVP:

- Terminal layer changes 1 to 7, with the round-trip and hold tests on the
  new API.
- `store`, `config`, `workspace`, `hook`, `mcp`, `harness` (Claude Code and
  Pi), `control`, `host`, and the commands `hypercube`, `stop [dir]`,
  `status`, `delete [dir]`, `mcp`, `hook`.
- Main-vertical layout, labels, borders, status bar with the path.
- Ctrl-] focus cycling.

Not in the MVP: `--all`, statusline and limits, scrollback, click to focus,
notifications, relaunching exited agents, detach and attach.

## Test plan

Terminal layer:

- The round-trip and hold tests pass after each change.
- Live tests, rebuilt from granite's on the runtime with a scripted child,
  for: adding a pane while others run; removing a pane and the
  repaint of its area; a fourth and fifth pane; focus moving off a removed
  pane; `send_key(Enter)` under legacy mode and under Kitty flags (the
  scripted child records its input); `close_pane` ending a child that ignores
  nothing and one that traps SIGHUP; an extra descriptor becoming readable
  wakes `wait`; a deadline wakes `wait`; children not inheriting other
  panes' masters.

Hypercube unit tests, ported from the Go tests and extended:

- `store`: update and rollback on error, concurrent updates from threads
  holding the lock, loading a Go-written state with `target` set.
- `config`: every validation error; `codex` is rejected.
- `workspace`: everything in `workspace_test.go`, against temporary
  repositories: worktree creation, exclude rule, `.worktreeinclude` copies,
  submodules, removal checks, removal of half-removed worktrees.
- `hook`: every event, block and idle transitions, facts for orchestrator,
  worktree worker, directory worker, `no_git`.
- `mcp`: schemas in both modes, each tool's validation, `create_agent`
  rollback when the host refuses the launch (with a fake control server).
- `harness`: exact argv and environment for Claude Code and Pi, with and
  without resume and prompt; the written Pi extension.
- `control`: request round trips; path length rule.

Hypercube integration tests, in the style of the live tests:

- Run `hypercube` in a pty with isolated `XDG_STATE_HOME`, `XDG_CONFIG_HOME`,
  a temporary repository, and `claude` and `pi` stubs first on `PATH`. The
  stubs are a small test binary that records argv and environment, runs the
  hooks the real harness would, and speaks enough MCP to call tools on
  command.
- Cover: first start creates the orchestrator and lays out one pane;
  `create_agent` adds a pane and a worktree; `send_message` to an idle stub
  produces the nudge text and Enter on its input; `remove_agent` closes the
  pane; `status` shows running; `stop` ends the host and every stub; a second
  start resumes with saved session IDs; `delete` refuses a dirty worktree and
  then succeeds.

Manual smoke tests with real harnesses: Claude Code `haiku` and Pi
`openrouter/~deepseek/deepseek-flash-latest`, in a disposable repository with
isolated state and configuration. Afterward, every test workspace is stopped
and its state, lock, socket, and repositories deleted.

Validation before pushing:

```sh
cargo build && cargo clippy --all-targets -- -D warnings && cargo fmt --check && cargo test
```

## Implementation plan

### Phase 0: terminal layer

1. `PaneId`, focus by ID, callbacks by ID.
2. `Rect` layouts and the `Chrome` trait. Remove the 1-to-3 assertion.
3. `add_pane`, `remove_pane`, `invalidate_chrome`.
4. `Pty::spawn` with cwd, environment, `FD_CLOEXEC`; `close_pane`; non-blocking
   reaping.
5. Bring in granite's `main.rs` host setup, host queries, and loop as
   `Runtime` with the step API.
6. `send_text` and `send_key` with the key encoder.
7. The scripted test child and the live tests from the test plan.

Each step keeps the round-trip and hold tests passing.

### Phase 1: hypercube MVP (this repository)

1. Done: Go in `v1/`; `Cargo.toml`, `.cargo/config.toml`, `Makefile`,
   `vendor/ghostty`, and the terminal layer and its tests at the root.
2. `store` and `config` with tests.
3. `workspace` with tests.
4. `harness`, `hook`, with tests.
5. `control` protocol and client.
6. `host`: host lock, socket, layout, chrome, launch, close, nudge with a
   200 ms Enter timer, teardown.
7. `mcp` tools on `control`.
8. Commands: `hypercube`, `stop`, `status`, `delete`, `mcp`, `hook`.
9. Integration tests with harness stubs, then real-harness smoke tests.
10. Rewrite `AGENTS.md` for the Rust version and its two harnesses.

### Phase 2: parity polish

`stop --all` and `delete --all`. Dropped (Claude Code's own status line covers
it): `hypercube statusline` writing limits to `<state dir>/claude-limits.json`;
the host reading that file every 15 seconds and drawing limits on the right of
the status bar; the Claude Code `statusLine` setting.

### Phase 3: terminal ergonomics

Scroll mode over Ghostty's scrollback (wheel when the focused program does
not track the mouse, and a key); click to focus; text selection and copy
through OSC 52; OSC 9 and 777 notification passthrough; relaunching an
exited agent with its saved session; zoom.

### Phase 4: detach and attach

Background host, client handoff of the terminal descriptor over the control
socket, `hypercube` attaching to a running workspace, input ownership when
the client goes away.

## Risks

- **Host input during the host query.** The runtime reads the host's replies
  before the loop starts; keystrokes typed then are consumed. Acceptable.
- **Claude Code's main-screen rendering.** Claude Code draws on the primary
  screen and relies on terminal scrollback; until phase 3, history above the
  pane is reachable only through Claude Code's own transcript view.
- **Notifications.** OSC 9 and 777 need either upstream libghostty support or
  a scan of pty output before it reaches the terminal.
- **Nudge timing.** The 200 ms gap between text and Enter mirrors the Go
  version. Whether nudges hold up while a harness dialog is open stays to be
  verified, as now.
