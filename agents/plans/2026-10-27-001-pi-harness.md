# Pi harness

## Goal

Hypercube can run workers and the orchestrator in Pi (`pi`, npm package
`@earendil-works/pi-coding-agent`). A profile with `"harness": "pi"` launches
Pi in its pane with the profile's model and effort, the Hypercube MCP server,
and message delivery through the same four hook events as the other harnesses.

## Related code

- `internal/harness/harness.go` — `Command` builds each harness's argv and
  environment. The `opencode` case writes an embedded plugin to
  `store.Dir()` with `HYPERCUBE_EXE` replaced by the executable path; Pi
  follows the same pattern.
- `internal/harness/opencode.js` — the OpenCode plugin. It maps harness events
  onto `hypercube hook <event>`, sends `{"session_id": ...}` on stdin, reads
  `hookSpecificOutput.additionalContext` and `reason`, runs SessionStart on the
  first prompt of each session, and answers a Stop block by prompting again.
- `internal/harness/config.go:86` — `Spec.check` lists the valid harnesses.
- `internal/harness/harness_test.go` — `TestOpenCodeModelSelection` runs the
  plugin under Bun with a fake API; `TestOxCommand` checks argv and settings.
- `internal/hook/hook.go` — hook handling. Unchanged: Pi uses the Claude Code
  response format like the others.

Pi's extension API, from the installed package's `docs/extensions.md` and
`dist/core/extensions/types.d.ts`:

- An extension is a JS or TS module whose default export receives `pi`.
  `pi --extension <path>` loads it for one launch.
- `pi.registerMcpServer(name, {command, args, env, exposure})` adds an MCP
  server for the session.
- `pi.on("before_agent_start", (event, ctx) => ...)` runs before each run
  started by a prompt or `pi.sendUserMessage()`. Returning
  `{message: {customType, content, display}}` adds a message that Pi sends to
  the model as user text.
- `pi.on("tool_result", ...)` can return `{content}` to replace a tool result.
  `event.parentToolCallId` is set for calls made by another tool, which never
  appear in the transcript.
- `pi.on("agent_settled", ...)` fires once Pi has no retry, compaction, or
  queued work left. `agent_end` fires before those, so it is not the Stop
  event.
- `pi.sendUserMessage(text)` starts a new run.
- `ctx.sessionManager.getSessionId()` is the session ID; `--session-id <id>`
  resumes that exact session, creating it if missing.

## Decisions

- **Launch command:** `pi --extension <ext> --model <model> --thinking
  <effort> --approve [--session-id <id>] [prompt]`. Models are Pi's
  `provider/id`, such as `openai/gpt-6.1-sol` or
  `openrouter/deepseek/deepseek-v4.1-flash-1017`. Effort is one of Pi's
  thinking levels. `--approve` answers Pi's project trust question for this
  launch, as Hypercube does for Codex, so a checkout with `.pi/` resources
  shows no dialog. Pi asks no tool permissions, so nothing else is bypassed.
- **Extension location:** `store.Dir()/pi-extension/index.js`, written on
  every launch like the OpenCode plugin.
- **MCP server:** registered by the extension, not a file, so the user's
  `mcp.json` stays untouched. `env` carries `HYPERCUBE_AGENT_ID`,
  `HYPERCUBE_STATE`, and `TMUX` from the extension's process environment,
  which the pane sets, and `exposure` is `"direct"` so the model sees the
  tools without searching.
- **Hook mapping:**
  - SessionStart and UserPromptSubmit: `before_agent_start`. The first run of
    each session ID in the process calls SessionStart, then every run calls
    UserPromptSubmit. The combined context is returned as a message with
    `customType: "hypercube"` and `display: true`.
  - PostToolUse: `tool_result`, skipped when `parentToolCallId` is set. The
    context is appended to `event.content` as a text block.
  - Stop: `agent_settled`. A returned `reason` is sent with
    `pi.sendUserMessage(reason)`, which starts a run whose
    `before_agent_start` marks the agent busy again.
  - Every call sends `{"session_id": ctx.sessionManager.getSessionId()}`.
- **No model check:** Pi resolves `--model` by exact ID first and passes an
  unknown ID to the provider, which rejects it in the pane. A partial ID can
  fuzzy-match another model, so the documentation says to use the full ID.
  Unlike the OpenCode plugin, the extension does not compare models.

## Test plan

- `TestPiCommand`: `Command` for a Pi agent with a session ID and a prompt
  returns `pi --extension <store.Dir()/pi-extension/index.js> --model m
  --thinking high --approve --session-id s1 <prompt>`, and without a session
  ID or prompt omits both. The extension file exists and does not contain
  `HYPERCUBE_EXE`.
- `TestPiExtension`, skipped when `node` is missing: write the extension with
  a fake executable, a shell script that appends its event and stdin to a log
  and prints a response (context for SessionStart, UserPromptSubmit, and
  PostToolUse; `{"decision":"block","reason":"queued"}` for the first Stop,
  nothing for later ones). Import the extension in Node with a fake `pi` that
  records `on` handlers, `registerMcpServer`, and `sendUserMessage`, and a fake
  `ctx` whose `sessionManager.getSessionId()` returns a fixed ID. Check:
  - `registerMcpServer` gets `"hypercube"`, the fake executable, `["mcp"]`,
    the agent ID and state path in `env`, and `exposure: "direct"`.
  - The first `before_agent_start` calls SessionStart then UserPromptSubmit
    and returns one message holding both contexts; the second calls only
    UserPromptSubmit. Each call's stdin carries the session ID.
  - `tool_result` with `parentToolCallId` calls nothing and returns nothing;
    without it, it calls PostToolUse and returns the original content plus
    the context.
  - `agent_settled` calls Stop and sends `queued` with `sendUserMessage`; a
    second `agent_settled` sends nothing.
- `config.go`: a profile with `"harness": "pi"` loads, and the error message
  for an unknown harness lists `pi`.
- Smoke test, in `~/projects/hypercube-smoke` with an orchestrator and a Pi
  worker on `openrouter/~deepseek/deepseek-flash-latest`: the pane label and
  model are right, the worker receives its first message from the nudge,
  `send_message` between the orchestrator and the worker works both ways
  including a nudge to an idle Pi pane, the worker goes idle after a turn, a
  message queued during a running turn arrives through PostToolUse or Stop,
  and `hypercube stop` then `hypercube` resumes the Pi session.

## Implementation plan

1. `internal/harness/pi.js`: the extension, in the style of
   `opencode.js`. `const exe = HYPERCUBE_EXE`; a `hook(event, sessionID)`
   helper that runs `exe hook <event>` with `node:child_process` `execFile`,
   writes the session JSON to stdin, and parses stdout (`{}` when empty); the
   MCP registration and the four handlers from Decisions; a `started` set of
   session IDs.
2. `internal/harness/harness.go`: embed `pi.js` as `piExtension`. Add
   `writePiExtension(exe string) (string, error)`, which writes it with
   `HYPERCUBE_EXE` replaced by `strconv.Quote(exe)` to
   `store.Dir()/pi-extension/index.js` and returns the path. Add a `"pi"` case
   to `Command` that calls it and builds the argv from Decisions. Update the
   package comment of `internal/hook/hook.go` to mention the Pi extension.
3. `internal/harness/config.go`: accept `pi` in `Spec.check` and its error
   message.
4. `internal/harness/harness_test.go`: `TestPiCommand` and `TestPiExtension`.
   `TestPiExtension` calls `writePiExtension` with the fake executable's path.
5. Run the smoke test above, then remove everything it created.
