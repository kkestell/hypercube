# Show Claude Code and Codex usage limits

## Goal

The user cannot see how much of their Claude Code and Codex subscription limits
they have used. When this work is done, the bottom of the sidebar shows one
row per harness that has reported its limits, for example
`Claude  5h 42% · 7d 18%`. Hovering a window shows when it resets. The rows
come from what running agents report through the plugin protocol; Hypercube
reads no credentials and calls no service.

The change touches the harness plugins and the plugin protocol, so an active
session reports limits only after it restarts.

## What the harnesses emit

Observed with Claude Code 2.1.317 and codex-cli 0.166.0, each run in a
temporary directory.

**Claude Code.** In `--output-format stream-json`, each turn emits one
`rate_limit_event` after the assistant message and before the result:

```json
{"type":"rate_limit_event","rate_limit_info":{"status":"allowed","resetsAt":1793767800,"rateLimitType":"five_hour","overageStatus":"rejected","overageDisabledReason":"org_level_disabled","isUsingOverage":false,"unifiedWindows":{"five_hour":{"utilization":0.01,"resetsAt":1793767800,"status":"allowed"},"seven_day":{"utilization":0.39,"resetsAt":1794193200,"status":"allowed"}}},"uuid":"bba296d8-e550-4e2e-9558-3baab3d2ebf7","session_id":"428dc0cd-bfe8-47fb-a7e2-f1ce210e95ce"}
```

`utilization` is a fraction of the limit (0.39 is 39%), and `resetsAt` is in
Unix seconds. Nothing is emitted before the first turn. Assumed: an account
billed by API key, without subscription limits, sends no `unifiedWindows`.

**Codex.** The app-server sends `account/rateLimits/updated` after each turn,
between `thread/tokenUsage/updated` and `turn/completed`, with no thread ID:

```json
{"method":"account/rateLimits/updated","params":{"rateLimits":{"limitId":"codex","limitName":null,"normalModelSlug":null,"primary":{"usedPercent":48,"windowDurationMins":10080,"resetsAt":1793792440},"secondary":null,"credits":{"hasCredits":false,"unlimited":false,"balance":"0"},"individualLimit":null,"spendControlReached":null,"planType":"prolite","rateLimitReachedType":null}},"emittedAtMs":1793750712115}
```

Nothing is sent at startup unless the client calls `account/rateLimits/read`.
The windows are not positional: this account has only a seven-day `primary`
window and no `secondary`, so a window is identified by
`windowDurationMins`. The generated schema
(`codex app-server generate-json-schema`) documents the notification as a
sparse update to merge into the last known values, makes
`windowDurationMins` and `resetsAt` nullable, and keys snapshots by `limitId`
(`rateLimitsByLimitId`), with model-specific quotas carrying their own ID.
`codex` is the ID observed for the account's general limit.

**OpenCode and Pi** report no subscription limits and are unchanged.

## Decisions

- **Protocol.** `Event` gains `Limits []Limit`. A `Limit` is the account's use
  of one usage window of the harness: `Minutes`, the window's length;
  `Used`, the percent of the limit used; `Resets`, when the window resets,
  in Unix seconds (zero when unknown); and `At`, when the plugin saw the
  harness's report, in Unix milliseconds. The window is named by its length
  because both harnesses can express it that way and the browser can label any
  length (`300` → `5h`, `10080` → `7d`). `Event.check` rejects a limit whose
  `Minutes` or `At` is not positive or whose `Used` is negative.
- **A reading updates the windows it names, when it is newer.** Codex
  documents its updates as sparse, so each reported window replaces the stored
  window of the same harness and length, and other windows stay. Claude always
  reports both windows. A reading replaces a stored one only when its `At` is
  later: after an app restart, `restoreFamily` starts one reader per surviving
  agent and each drains its retained output from its saved position, so
  agents' backlogs arrive in no shared order.
- **Readings live in the database**, in a `limits` table keyed by harness and
  window length. Each launch's events are handled once, and plugins keep
  running across app restarts without replaying them, so readings kept in
  memory would vanish at every restart until each harness finishes another
  turn. The table is created by `schema`'s `CREATE TABLE IF NOT EXISTS`, which
  upgrades existing databases with no other migration. Saving in the event's
  transaction reuses the existing refresh of the browser state. A stored row
  stays until a newer reading of the same window replaces it, including a
  window the harness no longer reports.
- **The harness is the session's harness**, the profile's ID such as `claude`.
  The core treats it as data and names no harness.
- **Claude plugin.** On `rate_limit_event`, report `five_hour` as 300 minutes
  and `seven_day` as 10080 minutes from `unifiedWindows`, with
  `Used = round(utilization × 100)`. Other window keys are ignored.
- **Codex plugin.** On `account/rateLimits/updated`, read `rateLimits` when its
  `limitId` is `codex` or absent, so a model-specific quota does not overwrite
  the general one. Report `primary` and `secondary` when present with a
  `windowDurationMins`. The plugin does not call `account/rateLimits/read`: the
  stored reading covers the time before an agent's first turn.
- **Display.** A `UsageLimits` component below Add Workspace shows one row per
  harness, ordered by harness ID, with windows ordered by length: the harness's
  display name, then `5h 42%` per window joined by ` · `. Each window's `title`
  reads `Resets Tue 3:40 PM` in the user's locale, and is omitted when
  `Resets` is zero (Codex allows a null `resetsAt`). A window whose `Resets`
  has passed keeps its last reported percent, dimmed, with the title
  `Reset Tue 3:40 PM`; this is worked out when the row renders, with no timer.
  With no readings it renders nothing.

## Implementation plan

1. `internal/harness/protocol.go`: add `Limit` (`minutes`, `used`, `resets`,
   `at` JSON fields) and `Event.Limits` (`limits`), with doc comments; validate
   limits in `Event.check`.
2. `internal/store/limits.go` (new) and `schema` in `internal/store/store.go`:
   add `CREATE TABLE IF NOT EXISTS limits (harness TEXT NOT NULL,
   minutes INTEGER NOT NULL, used INTEGER NOT NULL, resets INTEGER NOT NULL,
   at INTEGER NOT NULL, PRIMARY KEY (harness, minutes))`. Add `type Limit struct { Harness string
   \`json:"harness"\`; harness.Limit }`, `(*Tx).PutLimit(harness string,
   l harness.Limit) error` (insert, or update when the incoming `At` is later), and `(*Tx).Limits() ([]Limit,
   error)` ordered by harness, then minutes.
3. `internal/session/event.go`: count `len(ev.Limits) > 0` as `changed`, and in
   the save transaction put each limit under the session's `Harness` after
   reading the session.
4. `internal/ui/snapshot.go`, `internal/ui/socket.go`: `snapshot` also reads
   `tx.Limits()` in its transaction and returns them (an empty list when there
   are none); `dataSocket` keeps them beside `workspaces`, and `stateMessage`
   gains `Limits []store.Limit \`json:"limits"\``.
5. `plugins/claude/main.go`: decode `rate_limit_info.unifiedWindows` into
   `message`, handle `rate_limit_event` in `line` as decided, and emit an event
   that has limits.
6. `plugins/codex/events.go`, `plugins/codex/main.go`: handle
   `account/rateLimits/updated` with the other thread-less notifications at the
   top of `notification`, in a `rateLimits` function, and let `send` emit an
   event that has limits. If the leading `if` branches read poorly with a third
   case, turn them into a `switch` on `m.Method`.
7. `internal/harness/harnesstest/harnesstest.go`: the `!usage` event also
   carries `Limits: []harness.Limit{{Minutes: 300, Used: 42, Resets: …}}`.
8. Browser: `store.js` starts with `limits: []`; `data-socket.js`
   `receivedState` stores `message.limits`; export `displayName` from
   `profile-label.js`; add `sidebar/usage-limits.jsx` and
   `sidebar/usage-limits.css` (classes prefixed `usage-limits`, colors from
   `--vscode-descriptionForeground`, shared sizes), grouping `state.limits`
   with `Object.groupBy`; render `<UsageLimits />` after Add Workspace in
   `sidebar.jsx`.

## Test plan

- `plugins/claude`: new fixture `testdata/limits.jsonl` holding the recorded
  `rate_limit_event` line above; the plugin emits limits `{300, 1, 1793767800}`
  and `{10080, 39, 1794193200}`, each with a positive `At`.
- `plugins/codex`: new fixture `testdata/limits.jsonl` holding the recorded
  notification above; the plugin emits `{10080, 48, 1793792440}`. A
  notification with another `limitId` emits nothing.
- `internal/harness`: `Event.check` rejects a limit with zero minutes or
  negative use (add to the existing malformed-record cases).
- `internal/store`: `PutLimit` replaces the same harness and window and keeps
  the others; an older or equally old reading arriving after a newer one
  changes nothing; `Limits` orders by harness, then minutes; an existing database
  gains the table on open.
- `internal/session`: after `!usage` on a stand-in session, `Limits()` returns
  the stand-in's reading under the session's harness.
- `internal/ui`: the state message carries the stored limits.
- `internal/ui/web/sidebar/usage-limits.test.jsx`: rows per harness with
  labels `5h 42% · 7d 18%`, a reset `title` per window, the last percent kept
  and marked reset for a window whose reset time has passed, no title when
  `Resets` is zero, harness order, and nothing rendered without limits.
