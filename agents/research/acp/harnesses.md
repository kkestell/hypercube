# ACP harness support and reusable clients

Research date: **2026-10-29**. Scope: whether Hypercube can use ACP as its only harness interface, not a protocol-spec review. Read alongside `docs/agents.md` and the earlier `agents/research/harnesses/SUMMARY.md`.

## Evidence and limits

- **[verified]** means a local executable was queried, or an ACP `initialize` response was captured. The [local experiment record](#local-experiment-record) gives commands and complete capability responses. It does **not** mean a model/tool/permission interaction was tested.
- **[docs]** means official documentation or repository source inspected over HTTP; source inspection is not runtime verification. Links identify the evidence. Repository `main` and online documentation move; versions below are a dated snapshot, not a compatibility guarantee.
- `Y` = implemented/documented; `N` = explicitly unsupported; `?` = not established; `partial` = narrower than native terminal behavior. All unqualified capability cells below are **[docs]**, with the source in that row. Lack of evidence is not proof of absence.
- No adapters/packages were installed, downloaded for execution, or run. No authentication, `session/new`, prompt, or model call was made. No global configuration was changed. Installed native ACP servers were started only for `initialize`, then stopped.

## Bottom line for Hypercube

1. **ACP reaches most requested harnesses, but not with identical semantics.** OpenCode, Gemini, Copilot, Cursor and Goose have native entry points. Claude and Codex use substantial, actively maintained adapters; Pi, Amp and Aider use community adapters. The official list is an ecosystem directory, not a conformance certification. [docs: agents directory](https://agentclientprotocol.com/get-started/agents)
2. **The per-agent MCP identity is the first acceptance test, not chat rendering.** Pi's listed adapter accepts `mcpServers` but does not wire them into Pi. OpenCode installs supplied MCP servers at directory scope within its ACP process, so same-directory sessions can share/replace them. Cursor documents config-file MCP rather than `session/new` passthrough. These are material differences for Hypercube's lead/worker identity. [docs: Pi limitations](https://github.com/svkozak/pi-acp#limitations), [OpenCode MCP](https://opencode.ai/v2/docs/cli/acp/#mcp-servers), [Cursor MCP](https://cursor.com/docs/cli/acp#mcp-servers)
3. **Use one ACP process per Hypercube agent initially.** This is a design recommendation, especially to avoid OpenCode's directory-scoped MCP contamination; it is not a claim that the protocol requires one process per session. Hypercube must still own process cleanup, configuration, credentials, reconnect and transcripts. [docs: OpenCode process/session scope](https://opencode.ai/v2/docs/cli/acp/#transport)
4. **Claude subscription portability is a policy gate.** Its adapter uses the Claude Agent SDK. The adapter has Claude/Console login paths, but Anthropic's SDK overview says third-party developers may not offer claude.ai login or rate limits without prior approval. Do not promise that Hypercube can reuse a Pro/Max subscription just because another client can. API-key/approved-provider deployment is the supportable default pending clarification. [docs: SDK notice](https://code.claude.com/docs/en/agent-sdk/overview), [adapter auth implementation](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/src/acp-agent.ts)
5. **“Only ACP” can mean one transport, not zero harness knowledge.** Cursor has blocking vendor extensions for questions/plan approval; Claude/Codex have negotiated steering and richer AIR/subagent extensions. A core-only client will lose UX or functionality unless it handles unsupported requests deliberately. [docs: Cursor extensions](https://cursor.com/docs/cli/acp#cursor-extension-methods), [Claude adapter](https://github.com/agentclientprotocol/claude-agent-acp), [Codex adapter](https://github.com/agentclientprotocol/codex-acp)

### Claude adapter: parity and billing

- [docs] This is **Claude Agent**, not a remote control channel into a user's running Claude Code TUI. It loads SDK tools, permissions and context; it adds ACP translation and its own command/auth/config logic. The package authorship is Zed Industries and license is Apache-2.0; SDK/binary terms remain separate. [README](https://github.com/agentclientprotocol/claude-agent-acp), [package](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/package.json), [SDK terms](https://code.claude.com/docs/en/agent-sdk/overview#license-and-terms)
- [docs] It deliberately loads **user, project and local settings** (`settingSources: ["user", "project", "local"]`), so claiming that SDK use necessarily loses all CLAUDE.md, skills, plugins, hooks or MCP settings is wrong. The adapter builds its own hooks and merges user-provided hooks; not every SDK option/callback is representable across JSON-RPC. `_meta.claudeCode.options` is a harness-specific escape hatch, not portable ACP configuration. [source](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/src/acp-agent.ts), [SDK feature loading](https://code.claude.com/docs/en/agent-sdk/claude-code-features)
- [docs] Custom slash commands, TODO lists, nested transcripts, file review and terminal features are implemented. `/mcp reconnect/enable/disable` requires adapter-specific SDK control because Claude refuses those commands directly in SDK mode. Native TUI pickers, terminal layout, keybindings and native UI-only actions are not magically available. [README](https://github.com/agentclientprotocol/claude-agent-acp)
- [docs] The adapter has subscription/Console terminal auth paths and provider/gateway functionality, but **technical credential support is not authorization to distribute subscription-backed third-party access**. Anthropic's explicit SDK notice is the stronger deployment constraint. API calls use API/provider billing; ACP itself adds no alternate billing entitlement. [auth source](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/src/acp-agent.ts), [official restriction](https://code.claude.com/docs/en/agent-sdk/overview)
- [docs] Maintenance is high, but recent fixes include background permission cancellation, MCP startup failure reporting, replayed config/tool-call synchronization and plan approval IDs. Treat these as reasons to pin and regression-test versions, **not assertions those fixed bugs remain open**. Background children/commands may intentionally survive cancellation of a parent turn; `session/cancel` is not process-tree teardown. [changelog](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/CHANGELOG.md), [subagent cancellation semantics](https://github.com/agentclientprotocol/claude-agent-acp#subagent-sessions)

### Codex adapter: parity and billing

- [docs] Current adapter is TypeScript around Codex App Server, **not the earlier Rust implementation some older integration articles describe**. It bundles a compatible Codex npm dependency; overriding `CODEX_PATH` can break that tested pairing. `CODEX_CONFIG` merges session config. Existing native TUI is not attached. [README](https://github.com/agentclientprotocol/codex-acp), [package](https://github.com/agentclientprotocol/codex-acp/blob/main/package.json)
- [docs] Auth supports **ChatGPT login**, `CODEX_API_KEY`/`OPENAI_API_KEY` and opt-in client gateway auth. `NO_BROWSER=1` hides browser ChatGPT auth. Subscription credentials and API keys take their corresponding Codex billing paths; an API key is not required merely because ACP is used. [authentication](https://github.com/agentclientprotocol/codex-acp#authentication)
- [docs] Exposed commands include `/status`, `/mcp` (+reconnect), `/skills`, `/goal`, `/review`, `/review-branch`, `/review-commit`, `/compact`, `/logout`, and configured skills. This is not all native TUI commands. Native settings/hooks may remain underneath App Server, but adapter parity for every hook/plugin/UI feature was **not established**. [features](https://github.com/agentclientprotocol/codex-acp#features)
- [docs] Some rich controls are **AIR-only** or explicitly negotiated extensions: long-running goals, background-task stop/presentation, richer failures/diffs, and steering. Source also implements experimental ACP v2. Recent changes include subagent replay, host-owned idle steering fallback and disabling Visualize output that generic ACP clients show as raw text. [README](https://github.com/agentclientprotocol/codex-acp), [changelog](https://github.com/agentclientprotocol/codex-acp/blob/main/CHANGELOG.md)

### Native agents: important operational differences

- **OpenCode [docs].** ACP uses existing provider credentials and directory config (models, agents, commands, skills, instructions, plugins, MCP). `authenticate` does not itself collect credentials; terminal auth launches login separately. One active prompt per session; a second concurrent prompt errors. Persisted additional-directory grants also apply to other OpenCode clients using the session. Supplied MCP HTTP headers pass through **without OAuth**; same-name client servers replace configured ones at directory scope for the ACP process lifetime. This is the strongest concrete isolation caveat in this report. [reference](https://opencode.ai/v2/docs/cli/acp/)
- **Gemini [docs].** Source really merges `session/new.mcpServers` into per-session configuration: this improves on the earlier TUI-only report's “no per-process MCP” concern. The ACP guide misleadingly discusses MCP being supplied during initialize; actual source uses `newSession`/`loadSession`. Proxied filesystem support is real, but it is **not a sandbox guarantee**: native shell/tools can have their own host access. Six ACP command families currently registered are memory, extensions, init, restore, about and help; not the whole interactive command registry. Native auth/provider billing applies (Google account, Gemini API, Vertex as configured). [session manager](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/acp/acpSessionManager.ts), [command handler](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/acp/acpCommandHandler.ts), [auth docs](https://geminicli.com/docs/get-started/authentication/)
- **Copilot [docs].** Server-launch tool filters and reasoning effort become defaults for **every new/loaded session**, not per-session `session/new` inputs. Saved/enterprise sandbox policy still applies. BYOK provider mode can run ACP without GitHub login; otherwise normal Copilot entitlement/usage applies. Commands depending on TUI pickers (`/diff`, `/resume`, `/theme`, `/settings`, `/login`, `/help`, `/tasks`, `/undo`) are unavailable. **Unknown slash text is sent to the model**, so clients should use only the advertised list. [ACP reference](https://docs.github.com/en/copilot/reference/acp-server)
- **Cursor [docs].** Use existing `agent login`, `CURSOR_API_KEY` or `CURSOR_AUTH_TOKEN`; this is Cursor auth, not an Anthropic/OpenAI API key or an alternate subscription. `.cursor/mcp.json` works, dashboard/team MCP does not. Blocking `cursor/ask_question` and `cursor/create_plan` require responses; TODO/task/image notifications are nonblocking. A client implementing only generic text/tool/permission messages must at least return explicit errors/cancellation rather than silently leave vendor requests hanging. Standard plan mode is not equivalent to these request/approval UIs. [reference](https://cursor.com/docs/cli/acp)
- **Goose [docs].** Native desktop is itself now an ACP client, so the protocol is central rather than a thin community wrapper. Existing config, extensions, provider credentials and models carry over; `GOOSE_PROVIDER`/`GOOSE_MODEL` can override defaults. Goose prefers its own configured extension on a same-name MCP collision (opposite OpenCode's override behavior). Full desktop/recipe/provider/preferences features use many custom methods, so generic ACP will not reproduce the desktop UI. Its network server uses a secret and origin checks; prefer stdio for Hypercube rather than inherit another HTTP security surface. [GDK overview](https://github.com/aaif-goose/goose/blob/main/documentation/docs/gdk/acp/index.md), [MCP/config behavior](https://github.com/aaif-goose/goose/blob/main/documentation/docs/gdk/acp/zed.md), [server source](https://github.com/aaif-goose/goose/tree/main/crates/goose/src/acp)

### Community adapters: what is lost

- **Pi [docs].** Same underlying Pi session files can be resumed from Pi or ACP, but adapter additionally needs `~/.pi/pi-acp/session-map.json` for its IDs. Auth/provider setup is done in Pi; adapter terminal-login mode launches Pi rather than taking over billing. Skills and file prompts load, but extension slash commands do not. `/model` and `/clear` are replaced with client controls. Thought text is not a separate stream; embedded-context advertising is opt-in. Client FS/terminal are explicitly unsupported. Most importantly, this adapter's MCP limitation remains even though **installed Pi 1.4.0 itself has native MCP**: accepting a field does not pass it through the adapter. [README](https://github.com/svkozak/pi-acp), [source](https://github.com/svkozak/pi-acp/blob/main/src/acp/agent.ts), [verified native help](#local-experiment-record)
- **Amp [docs].** CLI transport preserves Amp login credentials and native thread IDs; `AMP_API_KEY` is supported for headless use. Config selects Amp's low/medium/high/ultra or discovered plugin modes, not arbitrary models. Default tool permissions are Amp policy/plugin behavior; **no interactive ACP permission-request bridge was found in server source**, so do not advertise Hypercube human approval parity. Optional **Orb execution uses SDK transport and ignores locally supplied permissions, MCP, skills and enabled-tool settings**, using remote project settings instead. [README](https://github.com/tao12345666333/amp-acp), [server](https://github.com/tao12345666333/amp-acp/blob/main/src/server.ts)
- **Amp [docs].** Resume depends on durable owner-only ACP→Amp thread mapping introduced in 0.10.0. Older sessions without mappings cannot be safely recovered; transcript replay is best effort if `amp threads export` fails. Never enable `AMP_ACP_CONTINUE_LATEST=1` for a team: it deliberately selects the installation's latest native thread, not the requested agent. [lifecycle notes](https://github.com/tao12345666333/amp-acp#native-amp-thread-lifecycle-extension)
- **Aider [docs].** The newer Python preview **changes Aider semantics**: git/autocommit is disabled; edits are staged in an overlay and flushed through client FS review (or disk fallback). `/commit`, `/diff`, `/undo`, `/git`, `/lint`, host editor/clipboard/voice/quit commands are omitted/rejected. No thread import/resume, no auth UI; requires API-key/provider setup and explicit `AIDER_ACP_MODELS`. Its issue link reports a Zed model picker limitation ([zed#59197](https://github.com/zed-industries/zed/issues/59197)); use slash model commands as documented, and verify issue status before relying on the limitation. [preview README](https://github.com/EnteRth3Void/aider_acp)

## 7. Acceptance tests before claiming a harness works

Recommended follow-up work (not performed; some requires a model call and disposable repo):

1. Two agents in the same cwd get differently authenticated Hypercube MCP servers; verify neither can call as the other, including after load/resume. Repeat with identical MCP server names.
2. Explicit-ID reload after process restart rebuilds history and reconnects the **same** per-agent MCP identity; never “latest”.
3. Exercise allow-once, deny-once, cancel while awaiting permission/question, then next prompt. No permanent stuck input or late tool approval.
4. Capture real plans, file diffs, model/effort/mode changes and advertised commands, with unsupported optional client capabilities disabled. Verify unknown vendor requests fail visibly rather than hang.
